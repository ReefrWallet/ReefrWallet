# ADR-029: Aptos support (node REST + indexer GraphQL)

* **Date:** 2026-10-13
* **Status:** Accepted
* **Context & Problem:** Aptos accounts need balances, transfers (APT, Coin standard, Fungible Asset), fees, and history for both Ed25519 and secp256k1 keys. The full-node REST API lists only transactions an account *sent*, so incoming transfers are invisible without the indexer. The indexer carries no transaction hashes, while broadcast records rows by hash.
* **Options Considered:**
  - History: node REST only (misses incoming transfers) vs. Aptos Labs indexer GraphQL (chosen).
  - Hashes: version as the identifier (breaks the broadcast row match) vs. one node lookup per indexed version (chosen).
  - Simulation: require the sender's public key in the builder (protocol change) vs. `NoAccountAuthenticator` (chosen).
* **Decision:**
  - Rust (`walletkit-ffi`): `AptosSignerFfi` derives addresses and signs. Ed25519 uses the legacy scheme; secp256k1 uses AIP-49 `SingleKey` (SHA3-256 digest, low-S ECDSA, `SingleSender` authenticator). `aptos_transaction_hash` matches node hashes. Byte-exact against `@aptos-labs/ts-sdk` 7.5.0 vectors (`Scripts/aptos-test-vectors`).
  - Paths: Ed25519 `m/44'/637'/i'/0'/0'`, secp256k1 `m/44'/637'/i'/0/0` (Aptos SDK).
  - Addresses: user input parses AIP-40 strict (long form, or `0x0`–`0xf`); chain data parses relaxed (node REST strips leading zeros).
  - `AptosClient`: REST for state, simulation, submission; indexer for bulk balances, metadata, history. One optional Aptos Labs API key as a bearer token (Settings `AptosAPIKey`, else `APTOS_API_KEY`). An RPC override keeps the indexer only on an `aptoslabs.com` host; otherwise history and bulk balances report unsupported.
  - APT is identified as `0x1::aptos_coin::AptosCoin`; its Fungible Asset form `0xa` normalises to it. Other paired assets map to their coin type.
  - History: heights are transaction versions. The head is the slowest of `account_transactions_processor`/`fungible_asset_processor`, so forward scans never pass unindexed versions. Effects are signed net amounts per asset: `.nativeTransfer` (no asset id) for APT, `.tokenTransfer` otherwise, so sync discovers tokens and refreshes balances. Pages hold 25 transactions (one node lookup each).
  - Builder: simulates with `NoAccountAuthenticator`, sets max gas to 2× used capped by balance, expiry from ledger time. Fee reserve is `max_gas × price`, which the node checks up front.
  - Dapps: an AIP-62 Wallet Standard provider (`providers/aptos.js`, `AptosDappProvider`) with account, connect, disconnect, network, onAccountChange, onNetworkChange, signMessage, signTransaction. The script returns duck-typed SDK objects (byte arrays with `bcsToBytes()`), so the wallet adapter can submit without the SDK in the page. `signTransaction` decodes the raw transaction fail-closed (entry functions only), checks sender and chain ID before prompting, and returns the `AccountAuthenticator`. Fee-payer and multi-agent transactions are refused. `signMessage` assembles the AIP-62 full message natively; its `APTOS\n` prefix can't collide with a transaction signing message.
  - Testing: `make aptos-testing` downloads Aptos CLI 9.6.0 (no mise entry); `AptosNode` runs `aptos node run-localnet` without the indexer (needs Docker). Indexer behaviour is covered by stubbed tests.
* **Consequences:** Aptos works for software keys with either curve. History needs the Aptos Labs indexer; custom nodes get balances and sends only. No Trezor support (no Aptos firmware protocol here), no APT/USD price source, no `signAndSubmitTransaction` (the adapter submits), and SDK `verifySignature` on the returned duck objects isn't supported.
