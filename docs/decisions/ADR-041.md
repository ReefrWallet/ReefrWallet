# ADR-041: Hardware key prompt HUD

* **Date:** 2026-10-21
* **Status:** Accepted
* **Context & Problem:** Hardware key operations (account derivation, transaction and message signing) gave no feedback when the device asked for confirmation, and failed with `notFound` when it wasn't plugged in. They start from views that are already sheets (`AddAccountView`, `TransferView` and its progress sheet, `DappRequestSheet`), two levels deep in places.
* **Options Considered:**
  - A `PresentedSheet` case on `MainView`: one sheet slot per view, so it would replace the sheet that started the operation and cancel its task.
  - A presenter shared by host views, shown by the topmost host: stacks over any sheet; hosts must be opted in.
* **Decision:** `HardwareService` owns a `@MainActor @Observable HardwareKeyPromptCenter` holding the current `HardwareKeyPrompt` ("Continue on \<vendor\>" / "Connect \<vendor\> to continue" / "Reading from \<vendor\>, please wait"; prompts name the vendor, e.g. "Trezor"). `.hardwareKeyPromptHost()` registers a view as a host; the most recently appeared host overlays `HardwareKeyPromptHUD`, a 200pt rounded square styled after Xcode's "Build Succeeded" HUD, with Liquid Glass on macOS/iOS 26+ (material before) and the content underneath disabled. An overlay, not a sheet: a sheet is a separate window, so its glass renders opaque. Hosts: `MainView`, `BrowserView`, `MainView`'s `PresentedSheet` content, `TransferView`, both `DappRequestSheet`s.
  - `connect(_:deviceId:)` shows "Connect" and polls every second until the device appears or the user cancels (`WalletKitError.userCancelled`).
  - `waitingForConfirmation` shows "Continue on". Device callbacks don't signal when the user pressed the button, so the prompt stays up until the enclosing `HardwareService.session` ends.
  - `session(showsWait: true)` shows "please wait" once the key is connected, until a confirm prompt or the session's end. Used for account creation, where exporting public keys is slow and often needs no confirmation.
  - A just-plugged Trezor fails its handshake with `deviceDisconnected` while booting, and `HardwareDeviceManager.connect` consumes the scanned entry, so `connect` rescans and retries after 1 s, up to 5 attempts.
  - A reply nobody read (a handshake failed mid-boot, an app quit mid-call) stays queued on the Trezor's USB endpoint across connections, so every later call reads the previous call's reply ("unexpected message type"). WalletKit's worker drains the endpoint with short-timeout rusb reads before connecting.
  - A session reruns its operation after 1 s, up to 3 attempts, on `deviceDisconnected`, so unplugging mid-operation shows "Connect" and then retries.
  - Dapp requests sign after their approval sheet closes, when no sheet can present (the host's own sheet is still dismissing). After a sign or send approval `DappRequestSheet` stays up until the request finishes, its host presenting a "Signing" progress popup that turns into the hardware key prompt in place, and on success into "Complete" for 1 s before dismissing (the dapp's response isn't delayed; `TransferView`'s send progress uses the same HUD) (`HostedPrompt`, `hardwareKeyPromptHost(progress:)`): `DappBridge`/`WalletConnectRequestRouter` run each request in `DappRequestScope` (a task-local id) and report `didFinishRequest(_:)`, which `DappApprover` matches against the approved request's id.
  - Only Trezor key stores run in sessions: the `.trezor` branches of `AccountService.makeAccount` and Cardano signing, and `TransactionService.withSigner(for:_:)` (transaction and dapp message signing, Sui account public key) when the key store is a Trezor. Local and watch-only keys never touch `HardwareService`. `makeSigner(for:)` stays for software-only callers.
* **Consequences:** Hardware code must run inside a session, or a "Continue on" prompt stays up. Sheets that can be open during device work must be hosts. With two windows open, the window that appeared last presents. PIN/passphrase input (`needsInput`) is still unhandled.

**Update (2026-10-24):** WalletKit's manager returns the already-open device on a repeat connect and keeps the delegate adapter from the first connection, whose weak reference to its `HardwareDevice` is nil once that object is released. Every sign after the first session then raised no "Continue on" prompt (seen with sequential approval revokes). `HardwareService` now keeps connected devices alive in a cache and reuses a still-connected one, so the original adapter stays valid; a wrong or disconnected device leaves the cache.
