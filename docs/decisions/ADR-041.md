# ADR-041: Hardware key prompt sheet

* **Date:** 2026-10-21
* **Status:** Accepted
* **Context & Problem:** Hardware key operations (account derivation, transaction and message signing) gave no feedback when the device asked for confirmation, and failed with `notFound` when it wasn't plugged in. They start from views that are already sheets (`AddAccountView`, `TransferView` and its progress sheet, `DappRequestSheet`), two levels deep in places.
* **Options Considered:**
  - A `PresentedSheet` case on `MainView`: one sheet slot per view, so it would replace the sheet that started the operation and cancel its task.
  - A presenter shared by host views, shown by the topmost host: stacks over any sheet; hosts must be opted in.
* **Decision:** `HardwareService` owns a `@MainActor @Observable HardwareKeyPromptCenter` holding the current `HardwareKeyPrompt` ("Continue on \<key\>" / "Connect \<key\> to continue"). `.hardwareKeyPromptHost()` registers a view as a host; the most recently appeared host presents `HardwareKeyPromptSheet`. Hosts: `MainView`, `BrowserView`, `MainView`'s `PresentedSheet` content, `TransferView` and its progress sheet, both `DappRequestSheet`s.
  - `connect(_:deviceId:keyName:)` shows "Connect" and polls every second until the device appears or the user cancels (`WalletKitError.userCancelled`).
  - `waitingForConfirmation` shows "Continue on". Device callbacks don't signal when the user pressed the button, so the prompt stays up until the enclosing `HardwareService.session` ends.
  - A session reruns its operation up to 3 times on `deviceDisconnected`, so unplugging mid-operation shows "Connect" and then retries.
  - Only Trezor key stores run in sessions: the `.trezor` branches of `AccountService.makeAccount` and Cardano signing, and `TransactionService.withSigner(for:_:)` (transaction and dapp message signing, Sui account public key) when the key store is a Trezor. Local and watch-only keys never touch `HardwareService`. `makeSigner(for:)` stays for software-only callers.
* **Consequences:** Hardware code must run inside a session, or a "Continue on" prompt stays up. Sheets that can be open during device work must be hosts. With two windows open, the window that appeared last presents. PIN/passphrase input (`needsInput`) is still unhandled.
