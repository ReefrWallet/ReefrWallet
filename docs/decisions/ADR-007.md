# ADR-007: Token discovery race fix

* **Date:** 2026-09-20
* **Status:** Accepted
* **Context & Problem:** Descending and ascending transaction sync run concurrently per account. Both can call `DatabaseService.fetchToken` for the same address, see no row, await RPC token metadata, then both call `insertToken`. `insertToken` never checked for an existing row — it always created a new `TokenModel` — so the race (and even non-concurrent repeat calls) produced duplicate token rows for the same `(address, blockchain)`.
* **Options Considered:**
  - Option A: Only make `insertToken` an upsert. Fixes duplication but leaves no DB-level guardrail if some other path ever inserts directly.
  - Option B: Add a DB unique constraint only. Doesn't fix `insertToken`'s "always create" bug, so ordinary sequential calls still error/duplicate depending on merge behavior.
  - Option C (chosen): Both — add `#Unique<TokenModel>([\.address, \.blockchain])` and rewrite `insertToken` as a real fetch-or-update-in-place upsert, centralized in one `upsertTokenModel` helper reused by `insertToken` and `DatabaseService+Balance.saveBalance` (which had its own duplicate fetch-or-create block).
* **Decision:** `TokenModel` now declares a composite unique constraint on `(address, blockchain)` using the existing `blockchain` relationship (no redundant stored field needed — SwiftData supports to-one relationships in `#Unique`). `DatabaseService.upsertTokenModel` fetches by that same key and updates in place, or creates once; `insertToken` and `saveBalance` both call it instead of duplicating the fetch-then-create logic. Because the actor method has no suspension point between fetch and write, this closes the race for any single call, and the unique constraint is a backstop against duplicate rows from any other path.
* **Consequences:** Only one `TokenModel` row can ever exist per address+blockchain, even under concurrent discovery from the descending/ascending sync tracks. Existing on-disk stores with pre-existing duplicate token rows (from before this fix) would fail SwiftData's lightweight migration validating the new constraint — not a concern pre-release, but worth a data-cleanup step before shipping if any real user data exists.

Unrelated: while validating this, found `WalletApp`'s `Inject.mode = .test` only activated on a `--test` launch argument, which plain unit tests (hosted in the app but not given that argument) never received — they fell through to the real on-disk `keystore.sqlite`. Added automatic detection via the `XCTestConfigurationFilePath` environment variable Xcode sets on any test host process, so all test runs now use the in-memory container regardless of launch arguments.
