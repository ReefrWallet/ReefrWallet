# ADR-021: Sui Wallet Standard provider + additive Ethereum Wallet Standard

* **Date:** 2026-09-30
* **Status:** Accepted, except the "Transaction building scope (v1 limitation)" bullet below — **superseded by ADR-023** (2026-10-02): that bullet's premise, that `toJSON()` returns base64 BCS bytes, is wrong, so `signTransaction`/`signAndExecuteTransaction` as shipped here never actually worked for any real dapp. See ADR-023 for the fix.
* **Context & Problem:** The dapp bridge (ADR-020) exposes Ethereum only, via EIP-1193/EIP-6963. Sui dapps use a different discovery/connection protocol, Wallet Standard, which registers a JS `Wallet` object into the page rather than a message-passing RPC. We need a Sui provider under that protocol, and — since Wallet Standard is cross-chain — an additive (not replacing `window.ethereum`) Wallet Standard registration for Ethereum too, for Wallet-Standard-only connection UIs.
* **Options Considered:**
  - Sui `signTransaction`/`signAndExecuteTransaction` handoff: (a) require the dapp to hand over an already-built/serialized transaction and reject anything else; (b) bundle a trimmed Mysten SDK transaction builder into the injected JS, with a client transport, so the wallet can resolve an unbuilt transaction itself; (c) reimplement Mysten's PTB-building/gas-resolution logic natively in WalletKit. (a) ships now with a documented limitation and no new JS/native dependency; (b) and (c) are real interoperability upgrades but substantial, independent projects.
  - Sui transaction-approval preview decoding: (a) show only raw bytes; (b) hand-write a fail-closed BCS reader for the fields this codebase's own encoders already prove out, rejecting every unrecognized variant; (c) decode in Rust against Sui's canonical `sui-types`. (b) was chosen — it's more informative than (a) without the new Rust dependency (c) would need, provided every unrecognized variant fails closed rather than being guessed at.
* **Decision:**
  - **Correction to ADR-020's "no core changes" claim**: adding this namespace needed two small, genuinely shared changes — `DappNamespace.providerScriptName: String` became `providerScriptNames: [String]` (a namespace can inject more than one script; Ethereum now injects both its EIP-1193 provider and an additive Wallet Standard wrapper), and `DappSession` gained `revokePermission(_:)` for Wallet Standard's `standard:disconnect` (EIP-1193 has no wallet-side disconnect concept, so nothing needed this before). Both are namespace-agnostic additions to the shared core, not Sui-specific carve-outs.
  - `SuiDappProvider` (new `DappProvider` conformer) implements `connect`/`disconnect`/`signPersonalMessage`/`signTransaction`/`signAndExecuteTransaction` — our own wire vocabulary between `providers/sui.js` and native, not Wallet Standard's JS-facing feature strings. `wireError` returns a plain `{message}` with no numeric code, since Wallet Standard (unlike EIP-1193) defines no error-code convention.
  - **Sign-time invariant**: `signTransaction`/`signAndExecuteTransaction` decode the dapp-supplied bytes and require the decoded sender to equal the authorized account before ever showing an approval prompt — a transaction that fails to decode, or whose sender doesn't match, is rejected outright (`.invalidParams`), never signed on the strength of a raw-bytes fallback.
  - **Fail-closed BCS decoder** (`WalletKit`'s `SuiTransactionDataDecoder`): recovers sender/gas budget/gas price/command count from a `TransactionData::V1` blob. Every `CallArg`/`Command`/`Argument`/`ObjectArg` variant is either mirrored byte-for-byte from this codebase's own tested encoders (`SuiUnsignedTransactions.swift`) or independently cross-checked against the discriminant-name strings embedded in the `sui` CLI binary (1.66.2) — `Pure`/`Object(ImmOrOwned|Receiving)` CallArgs, `TransferObjects`/`SplitCoins`/`MergeCoins` commands. Any other tag (`FundsWithdrawal`, `Object(Shared)`, `MoveCall`, `Publish`, `MakeMoveVec`, `Upgrade`, non-`None` expiration) fails the whole parse rather than being guessed at; canonical ULEB128, bounded collection counts, and exact-byte-consumption are all enforced. Real vectors (`TestVectors/sui-tx.json`, from `sui client ptb --serialize-unsigned-transaction` against a local validator) and adversarial/truncation cases both pass.
  - **Personal-message signing** needed new Rust FFI: `SuiSignerFfi::sign_personal_message` (BCS-`Vec<u8>`-wraps the message, prepends the `PersonalMessage` intent — scope `3`, not `TransactionData`'s scope `0` — Blake2b-256 hashes, signs), verified against known-answer vectors generated by the official `@mysten/sui` TypeScript SDK, not a same-crate self-consistency check. `SuiPKeySigner` now conforms to `MessageSigner` via a new `SignableMessage.suiPersonal(Data)` case.
  - ~~**Transaction building scope (v1 limitation)**: `providers/sui.js` calls `input.transaction.toJSON()` on the dapp's own `Transaction` object as-is (this is the literal `SuiSignTransactionInput` interface from `@mysten/wallet-standard`) and forwards the resulting base64 BCS bytes — it never attempts to build or resolve gas/sender itself. Dapps whose `Transaction` already carries its own client (the common case) resolve fine; a dapp expecting wallet-side resolution will see `toJSON()` fail in its own SDK. No SDK bundling, no native PTB builder.~~ **Superseded by ADR-023**: `toJSON()` returns a JSON data snapshot, not BCS bytes, so this never worked as described. ADR-023 adds a real JSON→BCS builder.
  - **Execution effects**: `signAndExecuteTransaction` returns the full spec shape (`bytes`, `signature`, `digest`, `effects`) via a new `SuiGRPCClient.executeTransactionWithEffects` (one execute call, widened read mask — no separate follow-up RPC) and `BlockchainClientProvider.suiClient(for:)`. Both are Sui-specific additions, not changes to the shared `BlockchainClientProtocol`/`TransactionService.sendTransaction` every other chain also uses.
  - Ethereum's additive Wallet Standard surface (`providers/ethereum-wallet-standard.js`) is discovery-only (`standard:connect`/`standard:events`; `standard:disconnect` is client-side-only) — generic Wallet Standard defines no EVM signing feature comparable to EIP-1193, so `window.ethereum`/EIP-6963 remains the only full-featured EVM surface.
* **Consequences:** Sui dapps that pre-build their transactions work end to end (discovery, connect, personal-message signing, transaction signing/execution with real effects) through the in-app browser. Dapps relying on wallet-side transaction building are not supported yet — a documented, deliberate v1 gap, not a bug. The BCS decoder's fail-closed design means new Sui protocol variants (new `CallArg`/`Command` shapes) will be rejected, not mis-signed, until support is added and verified against Sui's current type definitions — a safety-over-coverage tradeoff that will need revisiting as real dapp transactions exercise unimplemented variants. Permission revocation and multi-script injection are now shared-core concepts, so the next namespace (Solana, also Wallet Standard) should need even less new core work than this one did.
