# ADR-065: Blockscout token-transfer backfill

* **Date:** 2026-11-11
* **Status:** Accepted
* **Context & Problem:** The Blockscout history source backfilled only `/transactions`, which omits ERC-20 transfers in transactions the account didn't send. A token received before the first sync was never discovered, and forward sync starts above the stored head so it could not recover it. Etherscan's backfill already includes token transfers, so the same wallet synced differently by source.
* **Options Considered:**
  - Merge token transfers into the descending backfill (chosen).
  - A separate token-discovery pass only: smaller, but new accounts would need both passes.
  - Test-only change: leaves the product gap.
* **Decision:**
  - The descending backfill pages `/transactions` and `/token-transfers` together. The cursor holds both lists' positions; a cursor saved by an older version resumes the transaction list and restarts the transfers (writes are idempotent).
  - Accounts whose backfill finished earlier get one resumable pass over the transfer list only. `WalletTransactionSyncState` gains `tokenBackfillVersion` (0 = legacy, 1 = done) and `tokenBackfillCursor` (SwiftData lightweight migration: new properties with defaults). They are saved by their own `saveTokenBackfillProgress`, which never touches the sync cursors, so forward progress is preserved. Completing a normal backfill marks the account done. A source whose backfill already covers transfers (`tokenTransferHistory` returns `nil`) marks the account done without a pass. The pass logs and retries next session on failure rather than stopping the account's other tracks.
  - `BlockchainTransaction.isEffectsOnly` marks a record that carries only some effects of a transaction the source didn't list in full (an inbound transfer). Storing it adds the effects and never overwrites an existing transaction's sender, recipient, payload, status or method; a full record stored later replaces the placeholder's fields. Tested in both page orders through persistence.
  - Blockscout list items are skipped only when their `block_number` is explicitly null (pending). Any other item that doesn't decode fails the page, so a cursor is never committed past an unread record. A page with no confirmed items but a next page is followed.
  - A token whose metadata can't be read is skipped only for contract failures (undecodable return data, a revert); transient failures (timeout, quota) propagate so the page is retried. A skipped token is retried whenever one of its transfers is committed again.
* **Consequences:** Existing Blockscout-backed accounts repair their missing tokens once, in the background, then sweep balances. A pending transaction no longer fails a page. A permanently unreadable token is not persisted anywhere, so a token with a single historical transfer stays absent until it transfers again. Etherscan's own per-page synthetic records are not flagged effects-only yet.
