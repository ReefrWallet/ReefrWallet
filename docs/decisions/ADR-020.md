# ADR-020: Multi-chain dapp bridge (WKWebView), Ethereum first

* **Date:** 2026-09-25
* **Status:** Accepted
* **Context & Problem:** Reefr had no way to interact with dapps. A dapp browser needs to inject wallet providers into arbitrary pages, route requests to signing/broadcast, and gate everything behind explicit approval — for Ethereum first, with Solana/Sui, Tron, Cardano, and Bitcoin following the same seam later.
* **Options Considered:**
  - Option A: Build the bridge/session/approval plumbing directly against Ethereum's shapes: simpler now, but every later chain would mean re-deriving the same transport/permission/approval machinery from scratch.
  - Option B: A namespace-dispatched, chain-agnostic core (`DappProvider`/`DappSession`/`DappApproving`/`DappError`) with one JS provider script and one Swift conformer per chain: more upfront types, but each new chain is one provider file, one JS file, and one approval-detail view — the bridge, session, and window are never touched again.
* **Decision:**
  - A single `WKScriptMessageHandlerWithReply` (`reefr`), `.page` content world, main frame only, decodes `{namespace, method, params}` and dispatches to the namespace's `DappProvider`. `bridge.js` (transport + event bus) plus one provider script per namespace (`providers/ethereum.js` today) are injected at document start via `DappScripts`.
  - `DappSession` (an actor, one per browser window) holds the origin, the selected account per namespace, and in-memory `(origin, namespace, account)` permission grants, plus a serial approval queue so two dapp requests never present overlapping prompts. Switching account/chain via the browser's own picker or `wallet_switchEthereumChain` carries permission forward without a fresh prompt — the user, not the dapp, chose it.
  - `DappError` is a shared, chain-agnostic failure set; each provider's `wireError(_:)` maps it onto its own wire format — EIP-1193's numeric codes (4001/4100/4200/4900/4902/-32602/-32603) for Ethereum now, CIP-30's `APIError`/`TxSignError` for Cardano later.
  - `EthereumDappProvider` implements EIP-1193/EIP-6963: `eth_requestAccounts`/`eth_accounts` gated on `DappApproving.approve(.connect)`; `personal_sign`/`eth_signTypedData_v4` gated on `.signMessage` then `DappSigningService` (reusing `TransactionService.makeSigner(for:)` cast to the new `MessageSigner` protocol); `eth_sendTransaction` gated on `.sendTransaction` then `EthereumTransactionBuilder.buildCall`/`TransactionService.signTransaction`/`sendTransaction`; a fixed read-only allowlist passes straight through `EthereumRPCClient.request(method:params:)`; everything else is `.unsupportedMethod`.
  - `SignableMessage`/`MessageSigner` (WalletKit) cover EIP-191 personal messages and EIP-712 typed data. Hashing (`ethereum_personal_message_hash`, `ethereum_typed_data_hash`/`_fields`) and software signing (`EthereumSignerFfi::sign_digest`) are new Rust/UniFFI surface using `alloy-dyn-abi`. Trezor gets the full interactive `EthereumSignTypedData` struct/value walk on Model T/Safe (hand-rolled against `trezor-client`'s raw proto types, mirroring how `ethereum_sign_tx` already bypasses its convenience wrapper for PIN-hook interaction), falling back to `EthereumSignTypedHash` on Trezor One, whose firmware doesn't implement the full flow.
* **Consequences:** A dapp browser works end to end for Ethereum (connect, sign, send, chain switch, read-only RPC), with the entire bridge/session/approval/window layer chain-agnostic — adding Solana/Sui, Tron, Cardano, or Bitcoin later needs no changes here, only their own provider/JS/preview additions. Permissions are in-memory only for v1 (closing the window forgets every grant); persisting them, and the EIP-712 Trezor flow's `EthereumSignTypedData` implementation (untested against real hardware in this change), are follow-up work.
