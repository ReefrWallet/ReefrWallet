# ADR-012: Solana support (message-in-Swift, PDAs-in-Rust, envelope-based signing)

* **Date:** 2026-09-21
* **Status:** Accepted
* **Context & Problem:** `WKBlockchain` already had a `.solana` case and a placeholder `SolanaNetwork` with no real RPC URL, but no address type, client, builder, or signer. Reefr Wallet needs mainnet/testnet/devnet SOL and SPL account data, transfers (including sending to a recipient with no existing token account), history, fee estimation, and both software and Trezor signing.
* **Decision:**
  - **Split at the FFI boundary by what needs curve math vs. byte layout.** `walletkit-ffi::blockchain_clients::solana` (Rust) owns `SolanaAddressFfi` (Base58, on-curve check) and `find_program_address`/ATA/metadata-PDA derivation, since PDA search needs an ed25519 off-curve check. Legacy `Message` compilation/serialization (account-privilege-tier ordering, compact-u16, instruction encoding) is pure Swift (`SolanaMessage`/`SolanaShortVec`/`SolanaInstruction`), mirroring how `Sui/BCS.swift` stays Swift-side.
  - **`buildTransfer` returns a JSON envelope, not bare message bytes** (`SolanaUnsignedTransaction`: base64 message + per-instruction SPL token-account metadata), because Trezor's `SolanaSignTx` needs the ATA→owner/mint mapping to show a human-readable transfer on its trusted screen — the serialized message alone doesn't carry that. `SolanaPKeySigner`, `SolanaTrezorSigner`, `estimateFee`, and `broadcast` all decode this same envelope. Precedent: `TronUnsignedTransaction`.
  - **Native SOL and SPL share one `getAllBalances`.** Wrapped SOL's real mint address (`So111...112`) is used purely as a sentinel key for "native SOL" in the balances dict and `getTokenInfo`, the same role `"0x2::sui::SUI"` plays for Sui — so `.allBalances` covers both without a separate nil-token code path.
  - **SPL transfers always prepend an idempotent ATA creation for the recipient**, unconditionally (no existence check first) — `CreateIdempotent` is a no-op if the account exists, so this is simpler and race-free versus check-then-create. The sender pays the ~0.00204 SOL rent when creation is actually needed.
  - **All reads use `confirmed` commitment, not the RPC default `finalized`.** `finalized` lags `confirmed` by the ~32-slot optimistic-confirmation lockout (tens of seconds even on an idle single-node validator) — reading balances/history/blockhash at `finalized` right after this client's own broadcast would show stale pre-transfer state. `sendTransaction` sets `preflightCommitment: confirmed` to match its `confirmed`-fetched blockhash (a `finalized` preflight rejects a blockhash that recent as unrecognized).
  - **Token metadata**: `getTokenInfo` reads decimals from the mint account directly (fixed 82-byte prefix, same offset on Token and Token-2022) and name/symbol from the Metaplex Token Metadata PDA, falling back to a shortened mint string when no metadata account exists or parsing fails.
  - **Derivation path** `m/44'/501'/{account}'/0'` (SLIP-44 coin type 501, fully hardened per SLIP-10), matching Phantom/Trezor Suite.
  - **Trezor**: added `solana_sign_tx`/ed25519 `public_key` to `walletkit-hardware`'s `HardwareDevice` trait, implemented via `trezor-client`'s `solana` feature (`SolanaGetPublicKey`/`SolanaSignTx`, hand-rolled through `drive_interaction` like the Ethereum/Tron flows) in `walletkit-trezor`.
  - **Testing**: no `mise` registry entry exists for the Agave binaries, so `make solana-testing` downloads the official release tarball (bundles `solana-test-validator`/`solana`/`solana-keygen`/`spl-token` in one archive — SPL Token/Token-2022/ATA programs are already in the default genesis, no `--clone` needed) into `.build/solana-testing/bin/`, mirroring `make bitcoin-testing`. `SolanaLocalnetTests` exercises native transfer, SPL transfer with real ATA auto-creation, and history against a real validator; SPL instruction byte-layout and PDA-vs-mainnet-address correctness are covered by fast Rust/Swift unit tests instead of a second live-node path.
* **Consequences:** Software, watch-only, and Trezor-derived Solana accounts can receive, inspect history, and estimate/build/sign/broadcast native SOL and SPL transfers, including first-time sends to a recipient with no token account yet. Live coverage requires `make solana-testing`; devnet accounts need a funded key (airdrop-only, no committed key material).
