# ADR-022: Solana Wallet Standard provider

* **Date:** 2026-09-30
* **Status:** Accepted
* **Context & Problem:** ADR-021 added Sui as the second Wallet Standard namespace, alongside Ethereum's EIP-1193. Solana dapps also use Wallet Standard (`solana:signMessage`/`solana:signTransaction`/`solana:signAndSendTransaction`), but Solana's wire format is different enough from both Ethereum and Sui — legacy vs. version-0 messages, address-table lookups, no built-in sender/gas validation the way Sui's BCS decoder has — that it needs its own fail-closed parser, and its authorization model (required-signer slot, not fee payer) needs to support sponsored transactions Sui's model doesn't have to consider.
* **Options Considered:**
  - Transaction parsing depth: (a) decode only the header/account list, treating instructions opaquely; (b) fully decode instructions and version-0 address-table lookup *descriptors* (counts/indexes) without resolving what the lookup table's on-chain contents actually map those indexes to; (c) resolve lookup tables too, needing an RPC round trip before every preview. (b) was chosen: it's enough to validate every structural invariant (rules below) and preview fee payer/programs/instruction count, without adding a network dependency to what is otherwise a pure local parse.
  - Authorization model: (a) require the authorized account to be the fee payer (slot 0), matching a naive reading of "the wallet pays"; (b) require it to occupy any required-signer slot. (b) was chosen specifically to support sponsored transactions (a third party pays fees while this wallet only contributes a non-payer signature) — a real, common Solana pattern EIP-1193/Sui's model doesn't need to express.
  - JS-side test coverage: (a) skip automated JS tests, relying on native `SolanaDappProviderTests` plus manual in-app verification (the precedent ADR-021's Sui work actually left in place — no JS test infrastructure exists anywhere in this repo); (b) build a `JSContext`-based harness that loads the real `providers/*.js` files and exercises them directly. (b) was chosen (explicit ask, this ADR) — it catches script-level bugs (wrong feature version, broken variadic ordering, a `Uint8Array` never actually produced) native-side tests structurally cannot see, and is now reusable for Sui/Ethereum's own Wallet Standard scripts.
* **Decision:**
  - **New fail-closed parser** (`WalletKit`'s `SolanaParsedMessage`/`SolanaWireTransaction`, `SolanaWireTransaction.swift`): parses legacy and version-0 messages (version selected by the high bit of the message's first byte — legacy's first byte doubles as `numRequiredSignatures`, which is how Solana's own wire format distinguishes them), fully validates the wire-format invariants (canonical/bounded shortvec lengths via a new `SolanaShortVec.decodeCanonical`, exact input consumption, header counts consistent with the static account list, every `programIdIndex` a static account, every instruction account index within `totalAccountCount`, total account count within the one-byte index space, the overall size within Solana's ~1232-byte transaction ceiling) and rejects anything else outright. `SolanaWireTransaction.signed(by:signature:)` replaces exactly one signature slot, preserving every other (co-signer) signature untouched.
  - **Required-signer authorization, not fee-payer**: `SolanaDappProvider.validateAndSign` requires the authorized account to occupy one of the transaction's first `numRequiredSignatures` static keys — any of them, not specifically slot 0 — which is what makes sponsored transactions (this wallet signs a non-payer slot; some other party pays and co-signs) work. The preview separately surfaces `feePayer` (slot 0) so the approval screen doesn't imply this account is paying when it isn't.
  - **The broadcast signature, not the signer's own**: `signAndSendTransaction` returns whatever `SolanaRPCClient.sendTransaction`'s `sendTransaction` RPC call reports, decoded from Base58 to 64 raw bytes — never `result.signature` (this account's own signer-slot signature). In a sponsored transaction those two can be different signatures entirely (Solana's transaction identifier is always the slot-0/fee-payer signature); trusting the RPC's own report avoids this wallet asserting something about slot 0 it may not have touched.
  - **`signMessage` double rejection**: before any approval prompt, the raw message bytes are run through both `SolanaParsedMessage(validating:)` and `SolanaWireTransaction(parsing:)`; if *either* succeeds, the request is rejected. A message that happens to be structurally valid as a transaction message or a complete wire transaction must never be signable through the message-signing surface — that would let a malicious dapp get a transaction-equivalent signature under the guise of an opaque "message" the approval screen shows as arbitrary bytes. This is a safety-over-compatibility tradeoff: some genuinely-intended messages that coincidentally parse as valid Solana messages (extremely unlikely in practice, given the header/account-key layout) will be rejected too.
  - **Send options, including confirmation, are honored**: `SolanaRPCClient.sendTransaction(_:options:)` (widened from a fixed-behavior call) forwards `skipPreflight`/`maxRetries`/`minContextSlot`/`preflightCommitment` into the RPC's config (only when present — the prior hardcoded `preflightCommitment: "confirmed"` remains the default), and — new — the client itself polls `getSignatureStatuses` after broadcast when `options.commitment` is set, until that commitment is reached, the transaction fails on-chain, or a 30-second bounded timeout elapses. This is client-side polling, not a single RPC field; Solana's `sendTransaction` has no "wait for confirmation" option of its own.
  - **No Rust FFI for the software path**: Solana message signing (`SolanaPKeySigner` now conforms to `MessageSigner` via a new `SignableMessage.solanaMessage(Data)`) signs the raw bytes directly with the existing ed25519 `PrivateKey.sign(message:)` — no new intent-prefixing or hashing scheme the way Sui's personal-message signing needed, so no new Rust binding was necessary there. `SolanaTrezorSigner` originally stayed a plain (non-`MessageSigner`) `Signer`, since nothing in this codebase's Rust yet called the Trezor protocol's Solana message-signing command — superseded by the 2026-10-01 amendment below, which wires it up.
  - **`JSContext`-based Wallet Standard script harness** (`Tests/Support/DappWalletStandardJSHarness.swift`): loads `providers/wallet-standard-core.js` + a provider script directly into a bare `JSContext`, with minimal shims (`window` aliased to global, `btoa`/`atob`, a synchronous `addEventListener`/`dispatchEvent`/`CustomEvent`) and a native-backed `window.__reefr.request` the test controls per call. Every promise chain is created and resolved within a single `evaluateScript` call, since `JSContext` only drains its microtask queue synchronously at top-level script boundaries — attaching a `.then()` from native code after the fact does not resolve synchronously and would need real run-loop spinning. This is genuinely new test infrastructure (nothing like it existed for Sui/Ethereum's own scripts); `SolanaWalletStandardProviderScriptTests.swift` uses it to check declared feature versions/supported transaction versions, sequential variadic-input processing with preserved output order, `Uint8Array`↔base64 conversion in both directions, full option forwarding, and that native's `change` event payload replaces `accounts` directly (no extra request) — the one behavioral difference from `providers/sui.js`, which re-fetches via `connect` because native can't build a full account payload synchronously for Sui.
* **Consequences:** Solana dapps using the canonical Wallet Standard feature set can connect, sign messages, sign legacy/v0 transactions, and sign-and-send — including sponsored transactions where this wallet isn't the fee payer — through the in-app browser. The fail-closed parser means any Solana protocol surface this codebase doesn't yet understand (transaction version 1, resolved lookup-table addresses) is rejected outright rather than mis-parsed; this is a deliberate, narrower-than-ideal v1 surface, matching ADR-021's tradeoff for Sui's BCS decoder. Known v1 gaps, left for later: `solana:signIn`, transaction version 1, resolving address-table lookups for richer previews, simulation/balance-change previews, and the now-triplicated (Ethereum/Solana/Sui) browser account-picker pattern, which stays unrefactored. The new `DappWalletStandardJSHarness` is reusable as-is for adding equivalent script-level tests to `providers/sui.js`/`providers/ethereum-wallet-standard.js`.

* **Amendment (2026-10-01): legacy `window.solana` injection.** The v1 gap above ("legacy `window.solana`/`window.phantom` injection") is superseded — a direct-injection `providers/solana-legacy.js` was added alongside the Wallet Standard one, for dapps (and wallet-adapter's legacy fallback) that only look for `window.solana`, not Wallet Standard discovery.
  - **Options considered:** `signTransaction`/`signAllTransactions` depth — (a) duck-type against real `@solana/web3.js` `Transaction`/`VersionedTransaction` object shapes, since the dapp's own bundled web3.js already put the right methods (`serializeMessage`, `addSignature`, `message.serialize`, ...) on the object it hands us; (b) raw-bytes-only, reusing the Wallet Standard path verbatim; (c) skip these two methods entirely. (a) was chosen (explicit ask) for the closest match to real dapp expectations, accepting some risk if a dapp's web3.js version has a slightly different internal shape — a documented limitation, not a silent one.
  - **Decision:** `providers/solana-legacy.js`'s `signTransaction`/`signAllTransactions` extract the bare message bytes and existing signature slots from the dapp-supplied object (duck-typed: `transaction.message.serialize()` + `staticAccountKeys` for `VersionedTransaction`, `transaction.serializeMessage()` + `signatures[].publicKey` for legacy `Transaction`), assemble the exact same full wire-format bytes (`compact-u16(signatureCount) || signatures || message`) native's `SolanaWireTransaction` already expects, call the *same* native `signTransaction` method `providers/solana.js` uses, then write only this account's returned signature slot back into the same object (`addSignature`/direct `signatures[i] =` assignment) and return it — so a dapp's subsequent `.serialize()` call keeps working. This is a JS-side convenience layer only: every security-relevant check (fail-closed wire parsing, required-signer authorization, the RPC-reported broadcast signature) remains exactly as decided above, enforced natively regardless of which script produced the bytes.
  - **Identity stayed honest**: `window.solana.isReefr = true`; no `isPhantom`, no `window.phantom.solana` — matching `providers/ethereum.js`'s existing `isReefr`-not-`isMetaMask` precedent, at the cost of dapps that specifically gate discovery on `isPhantom` not finding this wallet via the legacy path (Wallet Standard discovery is unaffected).
  - **`connect({onlyIfTrusted: true})` needed one small native addition**: `SolanaDappProvider.connect` now reads `onlyIfTrusted` from `params` and throws `.unauthorized` immediately — before any approval prompt — when the origin isn't already permitted. Without this, a legacy dapp's silent-reconnect-on-page-load would show a connect popup every time instead of failing quietly. `providers/solana.js` never sends this key, so its own behavior is unchanged.
  - **`providers/wallet-standard-core.js` gained `bytesToBase58`**: Phantom's legacy `signAndSendTransaction` resolves `{signature: <base58 string>}`, unlike Wallet Standard's `Uint8Array` — only an encoder was needed (every base58 string this bridge produces starts from native-provided raw bytes; nothing decodes a dapp-supplied base58 string).
  - **Test coverage**: `Tests/SolanaLegacyProviderScriptTests.swift` reuses `DappWalletStandardJSHarness` against mocked legacy-`Transaction`- and `VersionedTransaction`-shaped objects (verifying only this account's slot is written and any co-signer entry is preserved untouched), plus `connect`/`disconnect`/`accountChanged` event derivation from native's single `change` event, `onlyIfTrusted` forwarding, and rejection of an unsupported object shape before any native call. `Tests/SolanaDappProviderTests.swift` covers the native `onlyIfTrusted` addition directly.

* **Amendment (2026-10-01): Trezor off-chain message signing.** The "Trezor off-chain message signing" v1 gap is closed. Investigation found the dapp-bridge gap was narrower than it looked: transaction signing via Trezor for Solana dapps already worked with zero dapp-specific code (`TransactionService.makeSigner`/`SolanaDappProvider` already dispatch any `.trezor` keystore generically to `SolanaTrezorSigner`). The actual gap was `solana:signMessage` — `SolanaTrezorSigner` wasn't a `MessageSigner`.
  - **The capability already existed, unwired**: the pinned `trezor-client = "0.1"` dependency (already built with `features = [..., "solana", ...]`) ships generated bindings for `SolanaSignMessage`/`SolanaMessageSignature`; nothing in this repo's Rust referenced them before this amendment.
  - **New Rust, mirroring existing precedent exactly**: a `solana_sign_message` method added through all four existing layers — the `HardwareDevice` trait (`walletkit-hardware`), the Trezor worker's `Command`/dispatch/wrapper (`walletkit-trezor/src/macos/worker.rs`), the actual `SolanaSignMessage`/`SolanaMessageSignature` protobuf exchange (`walletkit-trezor/src/macos/device.rs`, combining `solana_sign_tx`'s structure with `ethereum_sign_message`'s single-round-trip simplicity — Solana's off-chain message has no chunking or token-account metadata to carry), the non-macOS stub (`walletkit-trezor/src/unsupported.rs`), and the UniFFI export (`walletkit-ffi/src/hardware/device.rs`). No new error type or signature reshaping needed — the return is already the raw 64-byte ed25519 signature, same shape as `solana_sign_tx`'s.
  - **One Swift conformance closes the loop**: `SolanaTrezorSigner: Signer, MessageSigner`, `sign(message:)` calling `device.raw.solanaSignMessage(path:message:)`. No `SolanaDappProvider`/`DappSigningService` changes — the generic `signer as? any MessageSigner` dispatch already worked for `EthereumTrezorSigner`; this is the same precedent, not a new one.
  - **Verified, not just written**: `cargo check` (workspace), then `make walletkit-ffi` (full release cross-compile for macOS + iOS device + iOS simulator, UniFFI bindgen regeneration, xcframework rebuild) both succeeded, confirming `solanaSignMessage(path:message:)` reached the generated Swift bindings with the expected signature. `swift test --filter Solana` passed (67 tests), including two new `SolanaTrezorSignerTests` cases that follow this repo's existing real-hardware-integration-test convention (no-op without a physical device connected, same as every other Trezor test here).
