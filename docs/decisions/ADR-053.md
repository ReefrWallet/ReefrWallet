# ADR-053: Stored staking position

* **Date:** 2026-11-06
* **Status:** Accepted (implemented 2026-11-06)
* **Context & Problem:** ADR-052 read the Tron position live, so the Staking tab showed a spinner on every open and nothing offline, while balances were stored and refreshed in the background. Fee estimates also fetch the account's Bandwidth and Energy and threw them away.
* **Options Considered:**
  - Keep reading live: simplest, but no offline or instant tab, and resources fetched by fee reads are wasted.
  - Typed tables for votes, unstakes and resources: queryable, but nothing queries them and every chain-specific field is a schema change.
  - One row per account with a Codable chain-specific blob (chosen).
* **Decision:**
  - **Model:** `StakingModel`, one per account (`accountStableId` is unique; cascade-deleted with the account). Shared columns: staked and rewards (`BigUInt` as `Data`, like balances), `apr`, and a `.noAction` relation to the staked token (the chain's native token). Chain-specific data is `StakingDetails` JSON (`case tron(TronStakingDetails)`: the node's position and name and rate of each voted representative). An unreadable blob counts as no row and is refetched. A new entity and optional relation migrate automatically.
  - **Ordering:** each observation carries the time its request started. Position data is replaced only by a later one; Bandwidth and Energy have their own time, so a fee read can update them without making stake or reward data look fresh. Ties are discarded. `revision` rises with every applied write and is the UI's change signal. Rules live in `Staking.applying(...)`, run inside `DatabaseService`.
  - **Writers (Tron only):** `StakingStateService` is chain-agnostic: it decides when to read (`refresh`; `refreshAfterChange` after a transaction waits for any read already in flight, then reads once more, shared by concurrent callers) and delegates what to read and store to a `StakingPositionLoading` per chain family, so another chain adds a loader and nothing else. `TronStakingPositionLoader` is Tron's: it reads the position and best-effort representatives, and records results other code fetched anyway: `TronStakingService.prepare` and `state(for:)` (position, fee resources), `FeeEstimationService` and the dapp preview (resources). Resource-only records never create a row.
  - **Triggers:** `BalancesService.updateBalances` and the per-token queue drain (Tron has no all-balances call, so it bypasses `updateBalances`) read the position once per account, independently of balance success; the balance error is the one thrown and a failed position read is only logged. After a staking transaction confirms, balances and position are refreshed concurrently (spendable TRX changes too), the position once. Opening the tab refreshes it.
  - **Representatives are best effort:** the position is stored even if the lookup fails. Names and rates already stored for still-voted addresses survive a failed lookup or the node's fallback list (no names, no rates). The list is cached for an hour (a minute if degraded), per network and endpoint.
  - **UI:** the tab renders the stored row (`@Query`, keyed on `revision`). Sheets still read the live position before building and signing.
* **Consequences:** the tab opens instantly and works offline with last-known data; resource bars refresh whenever a fee is estimated. Stored data can be stale, so the live read stays authoritative for validation. A Tron account costs one extra round of node reads per balance update. Not covered by tests: balance success with a failing position read, and the single read after a confirmation, both need a reachable node.
