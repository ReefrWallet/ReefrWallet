# ADR-008: Debounced balance update queue

* **Date:** 2026-09-20
* **Status:** Accepted
* **Context & Problem:** `TransactionSyncService.maintainForwardSync`'s idle poll ran every 10 seconds once caught up, and on every iteration called `refreshBalances` unconditionally — a full `BalancesService.updateBalances` pass over every configured/stored token, even when the page it just fetched had zero new transactions. That's a recurring RPC cost paid at idle, not just when something actually changed.
* **Options Considered:**
  - Option A: Gate the existing full refresh on `!page.transactions.isEmpty`. Fixes the idle case but a burst of several transactions in one page still triggers one full-token-list refresh, and the live subscription path still did its own inline per-token RPC fetch on every discovered transfer.
  - Option B (chosen): Move all sync-driven balance work behind a debounced, per-token update queue on `BalancesService`.
* **Decision:** `BalancesService` is now an `actor` holding two queues: per-`(account, tokenAddress)` entries and per-account "full refresh" entries. `enqueueBalanceUpdate(account:tokenAddress:blockchain:)` adds/replaces an entry (`tokenAddress == nil` means the native asset) and (re)schedules a 1-second debounce; a repeat call for the same account+token before the timer fires replaces the pending entry instead of queuing a second one. If the account's client supports `.allBalances`, the account's queued per-token entries are purged and replaced with a single queued full refresh, since one bulk call is cheaper than N individual ones. `TransactionSyncService` no longer calls `updateBalances` at all — `commit` enqueues per discovered token when `updatesBalances` is true (the live per-head subscription path), and the boundary hooks either enqueue just the tokens touched by the page just processed (`refreshBalances`, a no-op on an empty page — this is what fixes the idle-poll cost) or, at the few points where earlier pages were deliberately committed without enqueueing (backfill completion, initial catch-up gap close), sweep every currently-known token once via `enqueueFullRefresh`. The UI (`SidebarView`'s manual refresh) keeps calling `updateBalances(_:)` directly for an immediate full resync, bypassing the queue entirely.
* **Consequences:** A quiet account now costs nothing at idle — no RPC calls fire until a page actually contains a transaction. Bursts of activity (e.g. catching up several blocks at once) collapse into one round of balance calls per account after a second of quiet instead of one round per transaction. `BalancesService`'s private per-token/`Token`-array helpers were re-expressed in terms of bare token-address strings (`Token`'s other fields were already unused past the initial `.address` lookup), which is what let the queue flush share the exact same RPC/persistence code the old full-refresh path used, with no behavioral change to that path itself.
