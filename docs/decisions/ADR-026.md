# ADR-026: Shared rate-limit handling for 3rd-party chain APIs

* **Date:** 2026-10-08
* **Status:** Accepted
* **Context & Problem:** `EtherscanTransactionHistorySource` is shared process-wide
  across every account's independent sync `Task`. Etherscan's V2 API is a single
  multichain host capped at 3 calls/sec, and `history()` fires two concurrent
  requests per page (`tokentx`/`txlist`); several accounts on one chain syncing
  concurrently blew through the cap constantly (`rateLimited("Max calls per sec
  rate limit reached (3/sec)")` in production logs). The existing retry loop
  reacted locally, per call site, after a failure, with no coordination across
  callers, and gave up after 3 attempts by falling back to slow full-node
  scanning. Cardano (Blockfrost), Tron (TronGrid), and Bitcoin (Esplora) had no
  rate-limit handling at all.
* **Options Considered:**
  - Per-call retry only (status quo): reacts after callers have already
    collided, doesn't prevent it.
  - A lock/semaphore serializing all calls to one host: blocks a thread per
    waiter, doesn't compose with structured-concurrency cancellation.
  - A shared, per-origin `actor` that paces dispatch and an Alamofire
    `RequestInterceptor` that reacts to real 429/503 (chosen): async-native,
    coordinates every caller (including a client recreated per call, like
    `CardanoClient`/`TronClient`) through one process-wide registry.
* **Decision:**
  - `RateGate<C: Clock>` (WalletKit, internal) is a FIFO-queue actor: `acquire()`
    suspends until a slot is free; `penalize(by:)` pushes the shared deadline out
    and reschedules every already-queued waiter, not just future ones. Generic
    over `Clock` so tests use a virtual clock instead of real sleeps.
  - `RateGateRegistry` (WalletKit, public) is the only access point: each client
    passes its own `ProviderKind` (`.etherscan`, `.blockscout`, `.esplora`,
    `.blockfrost`, `.tronGrid`, `.jsonRPC`) plus its endpoint's origin (scheme +
    host + explicit port — a self-hosted node on a different port is a different
    service). An exact-origin override takes precedence over a per-provider
    default, so an unlisted custom Blockfrost/TronGrid endpoint resolves to
    *that* provider's default, never a different provider's. `makeRetryPolicy(for:provider:)`
    returns a ready-to-attach `RateLimitRetryPolicy`; `penalize(origin:provider:by:)`
    is the one hook the Etherscan in-band path (below) needs.
  - `RateLimitRetryPolicy` (WalletKit, public, `RequestAdapter & RequestRetrier`):
    `adapt` calls `gate.acquire()` before every attempt — including retries, since
    Alamofire re-runs `adapt` for each one but never re-enters the Swift call site
    that dispatched the original request. `retry` reacts to real HTTP 429/503
    only (not general transport failures — timeouts/resets are a possible future
    extension, deliberately out of scope here), honoring `Retry-After` (numeric
    seconds or an HTTP-date, capped at 60s so a malformed header can't suspend an
    origin indefinitely) or falling back to jittered exponential backoff. Only
    429 calls `gate.penalize(by:)`; 503 is a general availability signal that may
    be unrelated to this client's request volume, so it doesn't depress every
    other caller's pace.
  - Every migrated `TargetType` sets `validationType: .successCodes` explicitly —
    Moya's default (`.none`) would otherwise keep Alamofire from ever invoking
    the retrier on a non-2xx response.
  - Proactive pacing is opt-in per confirmed origin, not assumed: `JSONRPCClient`
    (Ethereum + Solana), `CardanoClient` (Blockfrost), and `TronClient` (TronGrid)
    ship reactive-only (429/503 retry, no `RateGate`) since their real rate
    limits aren't confirmed, and `.jsonRPC`'s arbitrary endpoints (public default
    or a user's `rpcURLOverride`) have no single safe proactive number to assign
    site-unseen. Etherscan (2.5/sec), each Blockscout chain host (2/sec), and the
    public Esplora default (1/sec) have confirmed exact-origin rates.
  - Etherscan reports its limit inside an HTTP 200 body
    (`EtherscanResponse.init(from:)` throwing `EtherscanAPIError.rateLimited`),
    invisible to the interceptor. `EtherscanTransactionHistorySource.history()`
    keeps its own catch, calling `RateGateRegistry.shared.penalize(origin:provider:.etherscan:by:)`
    with the same backoff formula (`RateLimitRetryPolicy.backoffSeconds`) —
    the next `provider.request` call's own `adapt` then waits out the penalty,
    so no explicit sleep is needed.
  - A 429/503 retry can land on an "already known"/"already submitted" rejection
    even though the first attempt landed server-side. Each chain's broadcast
    path recovers its real identifier instead of surfacing a false failure:
    Ethereum hashes the signed RLP bytes (`ethereumKeccak256`); Bitcoin decodes
    the signed transaction via `bitcoinDecodeTransaction` and uses its `txid`
    (not a hash of the raw bytes, which would be the SegWit `wtxid`); Cardano
    hashes the *unsigned* `transactionBody` from the `CardanoUnsignedTransaction`
    envelope via `transactionBodyHash()` (not the complete signed CBOR, which
    includes the witness set); Tron promotes its unsigned payload's own `txID`
    out of fallback-only status; Solana parses the wire transaction via
    `SolanaWireTransaction` and reads `signatures.first` (not a fixed byte
    offset — the leading compact-u16 signature count is variable-length).
* **Consequences:** Every Etherscan call — across accounts and across the
  `tokentx`/`txlist` pair — now funnels through one shared pace comfortably under
  the 3/sec cap, and Blockscout/Blockfrost/TronGrid/Esplora gained retry handling
  they had none of before. Syncing many accounts on one chain is bounded by this
  pace rather than failing into slow node-scan fallback. Blockfrost/TronGrid/
  arbitrary-RPC proactive rates remain an open follow-up once their real limits
  are confirmed. Retry is intentionally scoped to HTTP 429/503; a transient
  connection failure during broadcast is not retried by this mechanism.
