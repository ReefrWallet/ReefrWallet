# ADR-023: Real Sui transaction building for signTransaction/signAndExecuteTransaction

* **Date:** 2026-10-02
* **Status:** Accepted (supersedes ADR-021's "Transaction building scope (v1 limitation)" bullet); JS builder superseded by ADR-032
* **Context & Problem:** ADR-021 claimed `input.transaction.toJSON()` is "the literal `SuiSignTransactionInput` interface" and returns base64 BCS bytes, which `providers/sui.js` forwarded as-is. That's wrong: `toJSON()` returns Mysten's "Transaction JSON" data snapshot (confirmed against the real `@mysten/sui` npm package), not BCS. `SuiDappProvider` then base64-decodes that JSON string and feeds it to the native BCS decoder, which always fails. Every real dapp's `signTransaction`/`signAndExecuteTransaction` call was broken, not just the "wallet-side gas resolution" cases ADR-021 scoped out.
* **Options Considered:**
  - (a) JS resolves the Transaction JSON into BCS itself, mirroring `@mysten/sui`'s own `Transaction.build({client})`, with native's own read-only RPCs standing in for the `client`. More JS, but needs no new native BCS encoder and keeps native's existing fail-closed decoder as the final gate.
  - (b) Do all resolution natively (parse the JSON in Swift, fetch chain data, build BCS in Rust/Swift). Avoids a second BCS encoder existing in two languages, but is a much larger, independent project (a JSON-schema parser plus a general PTB encoder, both new).
  - (c) Just correct the ADR text and leave `signTransaction` broken. Cheapest, ships nothing.
  - (a) was chosen.
* **Decision:**
  - **New script, `providers/sui-transaction-builder.js`**, injected before `sui.js` (`DappNamespace.sui.providerScriptNames`). Implements `build(transactionJSON, client, senderAddress) -> Promise<Uint8Array>`: resolves unresolved objects/pure values/Move-call signatures/gas, then BCS-encodes `TransactionData::V1` directly (hand-written ULEB128/u64/address/Move-type-tag-string writer — no bundled Sui SDK). `sui.js`'s `makeNativeClient` is the `client`, a thin adapter over `window.__reefr.request('sui', ...)`.
  - **Validated against the real SDK, not hand-derived:** three scenarios (fully-resolved transfer; unresolved shared object + untyped pure args via a MoveCall signature; generic MoveCall type arguments + `MakeMoveVec`) were built with the actual `@mysten/sui` package and saved as `TestVectors/sui-dapp-transactions.json`; `Tests/SuiTransactionBuilderScriptTests.swift` asserts byte-exact agreement, and `Tests/SuiWalletStandardProviderScriptTests.swift` asserts the same end to end through `sui.js`'s real `signTransaction`/`signAndExecuteTransaction`.
  - **`$Intent` commands (e.g. unresolved `coinWithBalance()`) are rejected outright, not resolved.** Tracing `@mysten/sui`'s source: `toJSON()` called with no arguments (the only way Wallet Standard calls it) always resolves every intent first or throws in the dapp's own code — a wallet calling the zero-arg `toJSON()` can never observe an unresolved `$Intent`. Implementing resolution for an unreachable case was dropped.
  - **New native read-only lookups** on `SuiDappProvider`: `getCoins`, `getObjects` (≤50 ids/call), `getMoveFunction`, `getReferenceGasPrice`, `simulateTransaction`. Each requires the same permitted-origin-and-matches-selected-account check `signTransaction` already does (`authorizedAccount`/a new `authorizedQueryAccount`), via a new `SuiDappChainQuerying` protocol `SuiGRPCClient` conforms to — the test seam `SuiDappProviderTests.swift`'s new fake implements. `simulateTransaction` additionally decodes and checks sender first, same invariant as signing.
  - **`SuiGRPCClient` gains `objects(ids:)` (`LedgerService.batchGetObjects`) and `moveFunction(package:module:name:)` (`MovePackageService.getFunction`)**, both converting their raw gRPC types into new WalletKit-public types (`SuiObjectInfo`, `SuiMoveFunctionSignature`/`SuiMoveParameter`/`SuiMoveTypeBody`) rather than leaking generated protobuf types across the WalletKit/app module boundary. `referenceGasPrice()` and a new `gasCostSummary(transactionData:)` (wrapping the existing internal `simulateGasCost`) are now public for the same reason.
  - **`SuiTransactionDataDecoder` gains `Command::MoveCall`, `ObjectArg::SharedObject`, and `Command::MakeMoveVec`** — mirrored byte-for-byte from `sui-types`' Rust definitions (cross-checked against the embedded discriminant/field-name strings in the `sui` CLI binary, 1.66.2, and independently against the real `@mysten/sui` SDK's own BCS output for the same shapes). `TypeTag` recursion is bounded (depth 16); Move identifiers are validated against Move's own grammar. `SuiTransactionDataSummary` gained `moveCalls: [SuiMoveCallSummary]`, shown in the approval preview as `0xab…cd::module::function`. `Publish`/`Upgrade`/`FundsWithdrawal`/non-`None` expiration remain fail-closed — a wallet has no meaningful way to preview raw Move bytecode or a funds-withdrawal source.
  - **Object classification (shared/owned/receiving) and mutability are usage-driven, not owner-driven** — mirroring `@mysten/sui`'s own resolver: an object is `Receiving` only if some `MoveCall` parameter's type is `0x2::transfer::Receiving<T>`; a shared object's `mutable` flag defaults to `true` unless every usage is a provably immutable Move reference (over-claiming mutable only costs scheduling concurrency; under-claiming it on a mutated object would be a real bug).
  - **Gas budget, absent an explicit one, is sized by one simulation** against a placeholder (empty-payment, max-budget) transaction via the new `simulateTransaction`/`gasCostSummary` plumbing, using the same formula as `@mysten/sui`: `max(computation + 1000·price, computation + 1000·price + storage − rebate)`.
* **Consequences:** Real Sui dapps using `signTransaction`/`signAndExecuteTransaction` now work end to end, including MoveCall, shared objects, and generic type arguments — not just the pre-built-transaction cases ADR-021 described as already working (which, per the premise above, never actually worked). `Publish`/`Upgrade`/sponsored transactions/`FundsWithdrawal` remain unsupported, a narrower and more accurate gap than ADR-021's "any wallet-side resolution" framing. The JS builder duplicates a chain-lookup `client` interface that only loosely mirrors `SuiClient`'s own shape; if Mysten changes the JSON format or resolution algorithm again, this file (and its real-SDK-sourced test vectors) need updating in lockstep, same as the decoder already did.
