# ADR-017: Cardano history pages pinned to a block window

* **Date:** 2026-09-24
* **Status:** Accepted
* **Context & Problem:** Once [ADR-016](ADR-016.md) gave Cardano a `head` and forward sync actually started running, `CardanoClient.transactionHistory` paged `accounts/{stake_address}/transactions` by ordinal page number alone. An ascending pass therefore began at page 1 in `asc` order — the account's *oldest* transactions — and reset its cursor to `nil` on the short final page, so every 10-second poll re-walked the entire history from genesis. Ordinal pages are also unstable under append: a transaction confirming mid-backfill shifts every remaining `desc` page by one and can drop a transaction at a page seam.
* **Options Considered:**
  - Sticky ascending page number: resume at the last page reached instead of resetting. No new API surface, but the first pass still walks the whole history, and `desc` page shifting stays unfixed.
  - Ascending scan in `desc` order, filtered by `lowerBound`. One request per idle poll, but multi-page catch-up still rides shifting page numbers.
  - Pin the page window with Blockfrost's `from`/`to` block-range parameters (inclusive, `block` or `block:index`).
* **Decision:** Pass `from`/`to` alongside `count`/`order`/`page`. Ascending pins the window's start, so a pass reads only the gap above what's synced; descending pins its end at `upperBound` (the head backfill started from), so mid-backfill arrivals can't renumber the remaining pages. The cursor became JSON — `{from, page}` — carrying the pinned bound across the pages of one pass; a bare-integer cursor from before this change still parses as a page number, so an in-flight backfill doesn't restart. An ascending pass that drains stores its resume point as `block:index+1` of the newest transaction it saw, at page 1: `lowerBound` is only block-granular, and resuming from it would re-read the head block on every poll and hand `TransactionSyncService` a non-empty page — and so a balance refresh — every 10 seconds, undoing ADR-008. For the same reason the `blocks/latest` fallback from ADR-016 now fires only for a caller with no head at all (`lowerBound` nil or 0, i.e. backfill), never on an idle forward poll.
* **Consequences:** An idle Cardano account costs one Blockfrost request per poll instead of one per history page. Correctness now depends on `from`/`to` being supported on this endpoint — verified only against Blockfrost's documented parameters and stubbed request assertions, not a live key; if they were rejected, history would fail outright rather than degrade. `tx_index` is decoded as optional, falling back to a block-granular resume point that re-reads one block rather than risking a skipped sibling transaction.
