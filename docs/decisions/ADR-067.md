# ADR-067: Build swift-atomics and swift-nio unoptimized

* **Date:** 2026-11-12
* **Status:** Accepted
* **Context & Problem:** The Release build crashed at launch, a few seconds in, when gRPC opened its first connection: a null dereference in `ManagedAtomic.init` (from `PendingStreamWritesManager.init`) or in `NIOSingletons.singletonsEnabledSuggestion`, which reads a global `ManagedAtomic`. Debug did not crash. The crash moved with build settings, so it is not NIO misuse (`singletonsEnabledSuggestion` is never set) and not our code. The cause is not found.
* **Options Considered:**
  - Whole-module and optimizer settings per target, bisected on Release launches: Atomics or NIO alone, `-Onone` alone (whole-module kept) and single-file alone (`-O` kept) all still crash. Atomics and the NIO Swift targets at `-Onone` with single-file together do not, with or without the gRPC targets and the C targets at `-O0`.
  - Build every dependency unoptimized: works, but slows code that does not need it.
  - Update swift-atomics and swift-nio: not tried yet.
* **Decision:** `Tuist/Package.swift` builds `Atomics` and the NIO Swift targets (`NIO`, `NIOConcurrencyHelpers`, `NIOCore`, `NIOEmbedded`, `NIOHPACK`, `NIOHTTP1`, `NIOHTTP2`, `NIOPosix`, `NIOTLS`, `_NIOBase64`, `_NIODataStructures`) with `SWIFT_OPTIMIZATION_LEVEL = -Onone` and `SWIFT_COMPILATION_MODE = singlefile` in every configuration. Everything else keeps the defaults.
* **Consequences:** Release launches and connects. NIO runs slower; fine for a wallet's request volume. Revisit when swift-atomics or swift-nio is updated or an upstream cause is found, then drop the setting. The same session fixed a separate Release-only crash: `@Query` predicates used `$0.account.id`, which SwiftData could not resolve in Release; they now use `persistentModelID` like every other predicate.
