# ADR-035: WalletConnect via Reown Sign SDK; shared Connected dApps list

* **Date:** 2026-10-17
* **Status:** Accepted
* **Context & Problem:** Dapps could only reach the wallet through the in-app browser (ADR-020…032). Users need external dapps (other browsers/devices) via WalletConnect, and a sidebar list of connected dapps. Browser permissions were in-memory only.
* **Options Considered:**
  - Option A: Reown's Sign SDK (`WalletConnect` product of reown-swift) + adapters onto the existing `DappProvider`s. Pros: one approval/signing path, relay/encryption/session storage handled, builds on macOS. Cons: type-name clashes with our `WalletKit`.
  - Option A2: `ReownWalletKit` (Sign + Pay + Push). Rejected: depends on the Yttrium xcframework, which has no macOS slice.
  - Option A3: upstream `reown-swift` as-is. Rejected: `LinkEnvelopesDispatcher.swift` uses `UIApplication` without a UIKit guard, so Sign doesn't build on macOS.
  - Option B: Implement the WalletConnect sign protocol ourselves. Cons: crypto/relay maintenance, security risk.
  - Option C: Mirror WC sessions into SwiftData rows. Cons: duplicate source of truth; sidebar only needs one entry.
* **Decision:** Option A, with `reown-swift` 2.4.0 vendored at `Vendor/reown-swift`: only the Sign targets, Yttrium/Pay/Push/AppKit removed, and `LinkEnvelopesDispatcher` guarded with `canImport(UIKit)` (link mode throws on macOS). Tuist references it via `.package(path:)`. Re-vendor from upstream and reapply that one-file patch to upgrade.
  - All Reown imports live in `ReownWalletConnectClient.swift` behind the `WalletConnectClient` protocol; everything else uses plain value types.
  - `WalletConnectRequestRouter` + `WalletConnectMethodAdapter` translate WC chain-RPC methods to the injected-provider shapes, so approvals, previews and signing are shared with the browser. Namespaces: eip155, solana, sui, tron, aptos.
  - Per request the router selects the account the user approved for that chain; the proposal approval is the consent recorded as the `DappSession` grant. WC sessions use a non-persisting `DappSession` per topic.
  - Sidebar "Connected dApps" holds browser entries (`ConnectedDappModel`, kind `.browser`) plus one "WalletConnect" hub entry (kind `.walletConnect`) whose detail lists live sessions straight from Reown's store. Sessions are not mirrored to SwiftData.
  - Browser grants are now persisted (`DappPermissionPersisting`, implemented by `ConnectedDappStore`) and restored when an origin is revisited. This amends ADR-020's in-memory-only permissions; grants stay bound to the selected account's address.
  - The Reown `projectId` is a constant in `WalletConnectConfig`.
  - Verify API: `scam` proposals/requests are rejected; `invalid`/`unknown` are shown in the proposal sheet.
  - Session-authenticate (SIWE) is unsupported: the `CryptoProvider` throws.
* **Consequences:** Browser and WC share signing and approval code. Pairing works from pasted `wc:` URIs, QR scan (iOS) and `wc:`/`reefr:` deep links. Non-EVM WC wire formats follow the WalletConnect chain specs but need interop testing per dapp.
