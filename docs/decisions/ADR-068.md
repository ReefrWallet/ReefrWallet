# ADR-068: TON (Gram) support, milestone 1

* **Date:** 2026-11-13
* **Status:** Proposed
* **Context & Problem:** WalletKit has no TON support. Milestone 1 takes a fresh software wallet from seed recovery to a confirmed Gram transfer, covering first-send deployment, fees and history reconciliation. Jettons, TON Connect and staking follow in later ADRs. Trezor has no TON app, so signing is software only.
* **Options Considered:**
  - Wallet V4R2: simple and widely supported, but its wallet ID is identical on mainnet and testnet, so a signed message can replay across networks when key and `seqno` match.
  - Wallet V5R1: TEP-3 recommended; the wallet ID is network-specific.
  - Derivation `m/44'/607'/i'` (TEP-3 multichain path) vs Ledger's TON path vs TON-native 24-word phrases (different algorithm). Only the first fits BIP39/SLIP-39 seeds.
* **Decision:**
  - **Chain/asset:** chain `ton`, native asset Gram (`GRAM`, 9 decimals), networks mainnet and testnet.
  - **Contract:** V5R1, workchain 0, wallet ID per network (pinned in code with test vectors). `TonAddress` derivation takes the network explicitly.
  - **Derivation:** Ed25519 SLIP-10 `m/44'/607'/i'`. BIP39/SLIP-39 seeds only; TON-native mnemonics and legacy V3/V4 wallets are not recovered. Restoring a seed must reproduce the original address.
  - **Hardware:** `HardwareDevice.account` throws `unsupportedFeature` for TON.
  - **Addresses:** both friendly base64 alphabets and raw `0:hex`; CRC16-XMODEM checked; bounce flag preserved; testnet-only tag rejected on mainnet. A non-bounceable tag sends without bounce (TEP-2). For raw input, a verified undeployed recipient is non-bounceable; a failed state lookup refuses rather than defaulting.
  - **Account state:** `nonexist`/`uninit`/`active`/`frozen`, separate from `isActiveAccount` (ever active). `frozen` never takes the fresh-deploy path.
  - **Send mode:** V5R1 external requests need the `+2` flag; the contract commits `seqno` before running out-actions, so a wallet transaction can exist without the payment. "Sent" requires the matching outgoing message in the wallet transaction; "delivered" requires recipient processing without bounce or failure. An undeployed recipient credited with its compute phase skipped is delivered.
  - **Ids:** `broadcast` returns the TEP-467 normalized external-message hash; history carries the wallet transaction hash; reconciliation maps one to the other.
  - **Data source:** toncenter v2 (state, `seqno`, `sendBoc`, `estimateFee`, `runGetMethod`) and v3 (history, traces); endpoint and API key configurable.
  - **Send pipeline:** the signed BOC, normalized hash, `seqno` and expiry are persisted before broadcast, under one process-wide lock. Deviation from reserving `seqno` before signing: the UI builds, signs and sends in separate calls, so a lock held across them would leak when a sign step is abandoned. Requests are built and signed outside the lock, so `send` re-reads the wallet `seqno` under the lock and refuses a request whose `seqno` was already used (`TonSendError.staleRequest`): two requests never both go out for one `seqno`. `sendBoc` is not replayed on a 503 by the HTTP layer (it can follow an accepted request); only a 429 refusal is retried. After an ambiguous failure the record stays and reconciliation reads wallet state first, resending the stored BOC only while its `seqno` is current and it is unexpired. If `seqno` advanced and the hash is not indexed, reconciliation walks the wallet's transactions from the latest one known when the request was built (`baselineLt`, stored with the record) to the chain's latest, checking each `prev_trans_lt` link. Only an unbroken chain with no transaction for the message proves it unprocessed; a gap, a short chain or a record without a baseline stays unresolved, and a replacement is signed only after that proof. No timeout decides it. An unreadable answer to `sendBoc` is ambiguous like a transport failure, so the record is kept.
  - **Delivery:** a confirmed sender entry proves the wallet emitted the message. History keeps the outgoing message hash (`TonDeliveryReference`); the app checks open sends on every poll, ten at a time rotating through all of them, however old, apart from the history cursor, and stores the recipient outcome (delivered or failed) in that payload. A stored outcome is final: re-importing the sender's history keeps it, and a failure keeps the entry `failed`.
  - **Empty history:** an account with no transactions has no head; sync starts forward from logical time 0 so the first deposit is picked up.
  - **Hardware:** TON is not offered for Trezor and the account service rejects it before connecting.
  - **History:** v3 with logical-time bounds (`lt` strictly increases per account): backward `end_lt = lastLT - 1`, forward `start_lt = lastLT + 1`, wrapped in an opaque cursor. `transactionHeads` and `.allBalances` stay unsupported (the latter until Jetton discovery).
  - **Cells:** pure-Swift `TonCell`/`TonBOC`; signing reuses the existing Ed25519 primitive.
  - **Account storage:** `AccountModel.publicKey` (optional `Data`, additive) keeps the raw key, since the V5R1 address is a hash of the state init and a first send must rebuild it. Set for local TON accounts only.
* **Consequences:** The app's sign-then-broadcast flow for TON becomes reserve, sign, persist, broadcast, reconcile. Users with TON-native mnemonics cannot import them. Address and message vectors come from a reference SDK. toncenter rate limits apply without an API key.
