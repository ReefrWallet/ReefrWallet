# ADR-003: Resumable Node-Native Transaction Synchronization

* **Date:** 2026-09-17
* **Status:** Accepted
* **Context & Problem:** The wallet must retain account activity across launches while full historical scans can run for a long time. It supports EVM and Sui now, must not depend on an indexer or backend, and must allow future chain-specific node capabilities without changing the local transaction schema.
* **Options Considered:**
  - Option A: Use an external indexer and webhook service: efficient account-history queries, but introduces credentials, a backend, and a third-party availability dependency.
  - Option B: Scan and subscribe through standard chain nodes: self-contained and portable, but EVM historical scans are expensive and node retention or capability limits can prevent complete history.
* **Decision:** Use Option B. Store normalized transactions, effects, and opaque per-account cursors in SwiftData. EVM and Sui maintain independent descending historical and ascending live-recovery cursors. The descending cursor retains its original head and never resets on interruption; forward scans preserve recent activity while backfill continues. Node adapters expose a capability-gated common transaction-history API so GraphQL or richer node sources can be introduced later.
* **Consequences:** Existing activity restores immediately from SQLite and all writes are idempotent across overlapping scans. Full history is only as complete as the selected node's retained data. The initial EVM adapter uses full-block standard RPC for direct sender/recipient activity; token-log and WebSocket subscription enrichments remain capability-specific additions rather than persistence-model changes.
