# ADR-030: TronLink-compatible Tron dapp provider

* **Date:** 2026-10-13
* **Status:** Accepted
* **Context & Problem:** Tron dapps (e.g. Symbiosis) only see wallets through TronLink's injected objects — `window.tronLink`/`window.tronWeb`, or TIP-1193 `window.tron` announced over TIP-6963 — mostly via `@tronweb3/tronwallet-adapters`. Reefr had no Tron namespace, so Tron accounts didn't even appear in the browser's account picker. Dapps build transactions with their own TronWeb and hand the wallet `{txID, raw_data, raw_data_hex}`; some also call the injected `tronWeb` for reads and building.
* **Options Considered:**
  - `window.tronWeb`: bundle the real TronWeb (works with dapps using the injected instance; ~940 KB) vs. a minimal shim (small; breaks those dapps). Bundled (explicit ask).
  - TronWeb's node HTTP: direct from the page (exposes the TronGrid key or goes unauthenticated, subject to page CSP) vs. relayed through native. Relayed.
  - What to validate/sign: dapp's `raw_data` JSON vs. `raw_data_hex`. `raw_data_hex` — the signature covers `sha256(raw_data_hex)`.
  - Trezor messages: firmware has no Tron message signing (`messages-tron.proto`, pinned rev and `main`); Trezor Suite's WalletConnect adapter also refuses `tron_signMessage`.
* **Decision:**
  - `DappNamespace.tron` + `TronDappProvider` (`connect`/`disconnect`/`network`/`signTransaction`/`signMessage`/`nodeRequest`). `providers/tron.js` injects `window.tronLink`, `window.tronWeb` (getter), `window.tron`, and a TIP-6963 announcement as "Reefr Wallet". Identity stays honest (`isReefr`, no `isTronLink`); the TronLink adapter finds it through its legacy `window.tronLink` fallback. Legacy `postMessage` events keep TronLink's `isTronLink: true` envelope only.
  - `vendor/tronweb.js` vendors `tronweb@6.5.1` `dist/TronWeb.js` verbatim (generated by `Scripts/tronweb`; `make vendor-js` regenerates it with the Sui SDK) inside a wrapper that evaluates it on first `tronWeb` access, without touching page globals. TronWeb's `HttpProvider` is subclassed to call `nodeRequest`; `trx.sign`/`signTransaction`/`signMessageV2` call native; hex-string signing, `multiSign` and typed data are refused.
  - `nodeRequest` forwards only `wallet/*`, `walletsolidity/*` (GET/POST) and `v1/*` (GET) through `TronClient.relay`, with the configured TronGrid key and shared rate limiting; network from the selected Tron account, mainnet otherwise. No permission needed (TronLink exposes reads pre-connect).
  - WalletKit `TronRawTransaction` decodes `raw_data_hex` fail-closed: one `TransferContract` or `TriggerSmartContract`, owner permission only, no TRC-10 call values, `auths`/`scripts`, unknown/repeated fields, negative `int64`s or trailing bytes. The provider checks owner == authorized account and `txID` == `sha256(raw)` before the prompt; `TronTransactionPreviewView` shows the decoded call (TRC-20 `transfer`/`approve`/`transferFrom` decoded; amounts in base units).
  - Signers get an envelope rebuilt from the decoded fields (`signingEnvelope()`), never dapp JSON. For Trezor, `isTrezorReproducible` (Rust `tron_raw_data` over that envelope) must equal `raw_data_hex` — Trezor signs its own re-serialization — else the request is rejected before the prompt.
  - Rust: `TronContract::TriggerSmartContract` gained `call_value` (parsed, re-encoded, and sent to `TronTriggerSmartContract`), so TRX-carrying contract calls are signable on Trezor.
  - `SignableMessage.tronMessage` + `TronPKeySigner: MessageSigner` implement TIP-191 (`signMessageV2`), matching TronWeb byte-for-byte. Trezor accounts get "not supported" before any prompt.
* **Consequences:** Tron accounts show in the browser picker and connect to TronLink-adapter dapps; software accounts sign transactions and messages, Trezor accounts sign transfers and contract calls. The page's TronWeb never sees the API key, but dapps' reads count against it. Every page loads `tronweb.js`'s source (only executed on first `tronWeb` use). Stake 2.0 stake/unstake/withdraw (`FreezeBalanceV2Contract` 54, `UnfreezeBalanceV2Contract` 55, `WithdrawExpireUnfreezeContract` 56) are decoded, previewed and signed (2026-10-14). On Trezor they go through `TronFreezeBalanceV2Contract`/`TronUnfreezeBalanceV2Contract`/`TronWithdrawUnfreeze` (firmware omits the default `BANDWIDTH` resource when re-serializing, as TronWeb does); every bandwidth/energy stake also grants TRON Power (votes), as in Tronscan's "Bandwidth + TRON Power"; only the rarely used power-only `ResourceCode.TRON_POWER` freeze is missing from Trezor's `TronResourceCode`, so that one fails the reproducibility check. `TronscanStakingUITests` stakes bandwidth and energy through Nile Tronscan with `REEFR_TESTNET_MNEMONIC` account 0. Voting, reward claims and cancel-all-unstake are decoded and previewed too (ADR-052). Not supported yet: resource delegation and other contracts, TRC-10, multi-sig, `signTypedData`, dapp-initiated network switching, token-decimal-aware previews. `call_value` on Trezor needs `make walletkit-ffi`; until then such requests fail the reproducibility check rather than mis-sign.
