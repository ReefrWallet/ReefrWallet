# ADR-025: Dapp approval integrity (fees, origin binding, strict tx parsing)

* **Date:** 2026-10-07
* **Status:** Accepted
* **Context & Problem:** Three ways an approval could differ from what got signed or granted:
  - `eth_sendTransaction` previewed estimated fees, then applied the dapp's `gas`/`gasPrice`/`maxFeePerGas`/`maxPriorityFeePerGas` after approval, over the user's edits.
  - `DappSession.grantPermission` used the session's mutable origin/account, so navigating while a connect prompt was open could grant the new origin.
  - Malformed `value`/`data`/gas fields silently fell back to defaults (e.g. bad calldata → plain transfer).
* **Options Considered:**
  - Fees: reject dapp overrides (simple; breaks dapps needing a fixed gas limit) vs. merge before preview (chosen).
  - Origin: cancel pending approvals on navigation (needs approver plumbing) vs. conditional grant (chosen).
* **Decision:**
  - `EthereumTransactionRequest` parses strictly: absent/`null` → default, malformed → `invalidParams` (-32602). Also rejects `gasPrice` mixed with EIP-1559 fields, priority > max fee, `gas` < 21 000, and differing `data`/`input`.
  - Dapp fee fields are merged into `Fees` before the prompt (`gasPrice` → both caps); `EthereumCallPreview` carries the gas limit and `hasDappFeeOverrides`. The approved (or user-edited) fees and preview gas limit are the only ones signed.
  - `grantPermission(_:origin:account:)` commits only if the session still has that origin and selected account; otherwise the connect fails with `.disconnected`.
* **Consequences:** Preview equals signed gas parameters. Previously tolerated malformed requests now fail. Sign/send approvals are still not re-checked against origin changes after approval.

* **Amendment (2026-10-15): approval integrity gaps found in review.** Four more ways an approval could diverge from what the user agreed to, all fixed:
  - **The permission carry-forward followed an automatic account switch.** `DappSession.setActiveAccount` carries a namespace's grant onto the newly selected account, justified by the user having chosen the switch. `BrowserAccountSelectionModel.reconcile`'s fallback pick isn't the user's choice: deleting a connected account handed the connected origin whichever account the fallback landed on, with no prompt. Options: drop the carry-forward entirely (re-prompts on every legitimate picker switch) vs. split the two callers (chosen). `replaceActiveAccount(_:)` sets the active account and grants nothing; `reconcile` and the first default pick use it, the picker and `wallet_switchEthereumChain` keep `setActiveAccount(_:)`.
  - **The Tron approval sheet could show an amount the transaction doesn't carry.** `TronTransactionPreviewView.callRows` sliced a truncated trailing ABI word short, while the TVM reads the missing bytes as zeros — 37-byte `transfer` calldata displayed `data[36]` base units and executed `data[36] << 248`. `argumentWords(_:)` now right-pads to 32 bytes, matching the VM.
  - **An unresolved prompt deadlocked later approvals.** `DappApprover.approve`'s continuation was only resumed by the sheet's buttons or its presentation binding; closing the browser window did neither, leaking the continuation and holding `DappSession`'s exclusive approval slot. `rejectPending()` is now called from `BrowserView.onDisappear` and before the sheet's "Close Browser" dismissal.
  - **`openExternally` accepted any URL scheme.** A page's `window.open` reaches it with no user gesture, so a dapp could have the system opener act on a `file:` URL or a custom scheme. Restricted to `http`/`https`.
* **Consequences:** A dapp must re-request access for an account the app picked on its own. Non-web `window.open` targets are dropped silently rather than handed to the OS. Sign/send approvals are still not re-checked against origin changes after approval.
