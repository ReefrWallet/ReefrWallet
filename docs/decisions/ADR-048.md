# ADR-048: EVM token approvals tab

* **Date:** 2026-10-24
* **Status:** Accepted
* **Context & Problem:** Users can't see or revoke the ERC-20 allowances their EVM accounts have granted. Allowances have no on-chain index; they must be reconstructed from `Approval` events.
* **Options Considered:**
  - `eth_getLogs` on the account's RPC: no extra dependency, but public nodes cap block ranges, so a from-genesis scan can take thousands of requests or never finish; per-token scans only cover tokens already in the database. Rejected.
  - Third-party approvals API (Rabby, Revoke.cash): more metadata, but a new external service.
  - Etherscan `logs/getLogs` (chosen): one filtered query by owner topic, already used for history with a user-supplied API key and rate gate.
* **Decision:**
  - `ApprovalModel` (SwiftData, lightweight migration) relates an account, a token and a spender, with the allowance and approval time; cascade-deleted with its account or token. The tab reads it with `@Query`, joining `BalanceModel` for the owned balance shown after the symbol, like the balances table.
  - `ApprovalService.updateApprovals` queries Etherscan `getLogs` for `Approval(owner = account)` from the last scanned block (minus a 32-block reorg overlap) to the node's head, skipping ERC-721 (4-topic) logs. A full last page re-starts the window at the newest block seen, since Etherscan serves only 10,000 results per query. Newly logged and already stored (token, spender) pairs are confirmed with an `allowance()` `eth_call`; zero allowances are dropped; the token is resolved or created.
  - `ApprovalScanModel` stores the scanned block per account, saved in the same transaction as the approvals, so only the first scan starts at block 0 (the transaction-history lesson of ADR-017).
  - The sidebar's global Update runs it after balances for supported EVM accounts; there is no per-tab refresh.
  - Revoke is `approve(spender, 0)`, built, signed and broadcast through `TransactionService`, one transaction per selected row, each confirmed (receipt polled up to 3 minutes) before the next is built, since the builder reads the nonce at `latest` and a pending revoke would be replaced. Stops at the first failure; the row is deleted on confirmation.
  - The Approvals tab (EVM accounts only) shows Asset (+ balance), Type, Approved Amount (one line), Approved Spender, My Approval Time, with row checkboxes, select-all and "Revoke Selected". Chains and API key follow `EtherscanTransactionHistorySource.supports`; otherwise the tab shows a notice.
* **Consequences:** Approvals show instantly from the store; Updates cost one to a few Etherscan calls. Needs an Etherscan key and a chain it covers. NFT/`setApprovalForAll` and Permit2 allowances aren't listed, and spenders show as addresses. Revoking N approvals takes N signatures and N block confirmations.

## Update 2026-10-24: Tron

* **Decision:** `TronApprovalService` (behind `ApprovalService`) reuses the same store, tab and revoke flow for TRC-20. Discovery reads the account's own TronGrid transactions (`v1/accounts/{addr}/transactions`, `only_from`, confirmed, ascending, paged by fingerprint) from the stored cursor (newest `block_timestamp` in ms, kept in `ApprovalScanModel`) and picks successful `approve(address,uint256)` calls; no Tron Approval-event index is queryable by owner. Each candidate is confirmed with `allowance` via `triggerconstantcontract`. Revoke builds `approve(spender, 0)` with `triggersmartcontract`, signs and broadcasts through `TransactionService`, and polls `gettransactioninfobyid` for `SUCCESS` before deleting the row. Needs no API key (TronGrid key is used if set).
* **Consequences:** Approvals granted through other contracts (e.g. `increaseApproval`, multisig or permit flows) aren't discovered. Revokes cost energy/TRX like any contract call (fee limit 100 TRX).

## Update 2026-10-24: automatic refresh

* **Decision:** Approvals no longer refresh only from the sidebar's Update. `ApprovalService.refreshAll` runs once after `TransactionSyncService.startAll` at launch, and `TransactionSyncService.commit` calls `enqueueRefresh(account)` when a forward-sync page holds a transaction sent by the account. Refreshes are per-account background tasks; calls during a run coalesce into one follow-up. The scan cursor keeps each run to new blocks/transactions.
* **Consequences:** An approve/revoke made in or outside the app appears once its transaction syncs. A refresh costs one Etherscan/TronGrid query plus one `allowance` call per stored approval.

## Update 2026-11-10: revoke review

* **Decision:** The toolbar opens the shared Transaction Sheet for one selected approval at a time. It shows the signing account, token contract, spender, zero allowance, and editable transaction fees. Revoke signs the transaction using the confirmed fees. Cancel stops the queue. Each success must confirm before the next review is prepared.
* **Trade-off:** Review adds network reads and a confirmation per transaction. Ethereum updates the displayed cost from the edited gas price cap and checks the nonce before signing. Tron validates the node-built call and shows bandwidth, energy, estimated TRX burn, and the energy fee limit. An unavailable quote prevents confirmation.

## Update 2026-11-10: chain services

* **Decision:** `EthereumApprovalService` and `TronApprovalService` each scan, prepare, submit and confirm their own approvals. Callers route by chain. Both services reuse the same refresh queue logic so overlapping background requests for an account still coalesce.

## Update 2026-11-10: first scan of busy accounts

* **Decision:** A new account enqueues an approvals refresh when it starts syncing. The EVM `getLogs` scan retries Etherscan's in-band rate-limit replies through the shared gate, like transaction history (ADR-026).
* **Consequences:** A concurrent history backfill no longer fails the first scan and leaves the tab empty until the next trigger.
