# ADR-001: Batched Token Balance Queries

* **Date:** 2026-09-03
* **Status:** Accepted
* **Context & Problem:** Refreshing several ERC-20 balances with one `eth_call` per token is expensive on metered RPC providers and does not guarantee a single block view. Sui already exposes all owner balances through `ListBalances`.
* **Options Considered:**
  - Option A: Keep individual balance calls: simplest, but retains provider cost and latency.
  - Option B: Add a bulk client API backed by Sui `ListBalances` and Ethereum Multicall3, with JSON-RPC batch fallback: reduces calls where Multicall3 exists while preserving EVM compatibility.
* **Decision:** Add `getBalances(owner, tokens:)` to the shared client protocol and type eraser. Ethereum uses Multicall3 `aggregate3` with per-call failure allowed, omitting failed token results; if the aggregate call itself is unavailable or fails, it uses a JSON-RPC batch. Multicall3 addresses are selected by chain ID with the canonical address as the default. The application balance refresh uses this API for ERC-20 tokens.
* **Consequences:** Supported EVM networks use one block-consistent aggregate request and metered providers charge for one top-level call. Networks without Multicall3 retain compatibility through JSON-RPC batching. A failed individual token no longer prevents successful token balances from being returned, and callers must treat omitted entries as unavailable/zero according to their domain policy.
