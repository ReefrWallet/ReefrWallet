# ADR-071: TON Jettons, milestone 2

* **Date:** 2026-11-15
* **Status:** Proposed
* **Context & Problem:** Gram works end to end (ADR-070). Jettons (TEP-74) are the other thing a TON wallet holds and sends. A Jetton credit can land on the owner's Jetton wallet with no transaction on the owner's wallet, so M1's history, delivery and balance paths cannot see it. Fees are not knowable from the first message alone: the Gram attachment depends on the Jetton contracts and on whether the recipient's Jetton wallet must be deployed.
* **Options Considered:**
  - Trust the indexer for balances and the spendable amount vs read the owner's Jetton wallet on chain. The indexer is incomplete and can lag.
  - Fixed 0.05 Gram attachment vs sizing it by emulating the real message.
  - Follow only the owner wallet's cursor for Jetton history vs a second scan over the provider's `actions`.
* **Decision:**
  - **Identity:** a master is its workchain and hash, never its string; parsed with `TonAddress` at every boundary (storage, history, listing, pricing). Pricing asks CoinGecko in one canonical form (mainnet, bounceable) under platform `the-open-network`; the cached token listing is versioned (`TokenListing.version` 2) so older listings without TON are discarded.
  - **Balances:** `.allBalances` returns Gram plus every Jetton of a complete `jetton/wallets` scan. Discovery never clears a holding: a Jetton missing from a complete scan is zeroed only after a targeted on-chain check (`get_wallet_address`, then `get_wallet_data`) shows zero or an absent wallet. A failed check or page keeps stored values. A frozen or mismatched Jetton wallet is unreadable, not empty. Sends read the spendable balance the same way.
  - **Transfer:** `transfer` (`0x0f8a7ea5`) to the sender's Jetton wallet, bounceable, random 64-bit `query_id`, `response_destination` = sender, forward amount 1 nanogram plus the optional comment. Sending is disabled while metadata is unresolved; TEP-64's default of 9 decimals applies only to resolved metadata that omits it.
  - **Fees:** the real message is emulated (`/api/emulate/v1/emulateTrace`) with a zero signature and `ignore_chksig`; a validly signed BOC never leaves the device before approval. The attachment is the first of 0.05, 0.1, 0.25 Gram whose trace credits the recipient. Credit is proven only along the transfer's own path (sender hop, then recipient hop matching opcode, source and `query_id`); an incomplete trace is inconclusive unless it shows an explicit refusal. The UI shows Gram required (attachment plus wallet fee reserve, what the balance check uses) apart from the expected net cost.
  - **Delivery:** the Jetton request row stays unconfirmed until the trace credits the recipient. A failure is read from the exact transaction that processed the first outgoing message, never from the destination. The `query_id` links the local placeholder, whose effect is the token amount (never the attachment), to the confirmed history entry.
  - **History:** a second sync track scans `actions` (`jetton_transfer`) apart from the wallet's `lt` cursor. A backward scan fixes its upper bound (`trace_end_lt`) so pages don't shift; a forward watermark then rescans an overlap of 100,000,000 lt and deduplicates by full action id. Progress is stored in two optional `Data` fields on the sync state (`jettonBackfillCursor`, `jettonForwardState`), an additive schema change. An effect's key is the full action id; its index is a 60-bit prefix.
  - **Parsing:** BoC reads are bounded (headers, 8-byte fields, depth ≤ 1024).
  - **Errors:** an HTTP 5xx from a JSON-RPC node is `BlockchainClientError.serverError(status:)`, ambiguous for submissions, never a rejection. A provider-wide failure ends a CoinGecko pass and makes the scheduler back off without stamping tokens failed.
* **Consequences:** Reading a Jetton needs several toncenter calls, and sizing an attachment up to three emulations, so quotas matter without an API key. Scam or lookalike Jettons are listed like any other; none is trusted automatically. Platform strings are still passed as `String` (a typed address kind was declined for now). Reference-SDK vectors for the transfer body and the live testnet fixture are still to add; the UI test needs RTJ held by account 0.
