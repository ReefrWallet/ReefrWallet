# ADR-064: Request lanes per connection

* **Date:** 2026-11-10
* **Status:** Accepted (amends ADR-026)
* **Context & Problem:** One FIFO `RateGate` per origin made balance, staking and approval requests wait behind a long transaction backfill on the same origin. Origins without a confirmed rate had no queue, so a backfill burst drew 429s that hit every caller. Sui gRPC and Electrum had no rate handling.
* **Options Considered:**
  - Strict priority: a lower lane runs only when higher ones are empty. Starves backfill.
  - Separate gates per purpose: each would need its own rate, so the origin's budget is exceeded.
  - Weighted fair lanes inside one gate per origin (chosen).
* **Decision:**
  - `RequestLane` (`interactive` 16, `polling` 8, `balances` 8, `approvals` 4, `backfill` 1) is a task-local; unlabelled work is `interactive`. Service task roots set it: sync backfill, sync polling, balances/staking/price/identity, approvals.
  - `RateGate` keeps a FIFO per lane and admits by stride scheduling. A lane gets no credit for idle time.
  - The lane is stamped on the request in Moya's `requestClosure` (synchronous, on the issuing task) via `URLProtocol.setProperty`; `adapt` reads it on every attempt. `RateGateRegistry.makeProvider` replaces the duplicated session setup.
  - Every origin has a gate. Unconfirmed origins are adaptive: unpaced until a quota signal, then `paced` at half the measured rate (floor 1/s), growing 10% per 15 s interval only with enough successes, capped at 0.8 of the failed rate. After 30 s without backlog a `probing` trial admits at most 2x the proven rate; it returns to unpaced only after 60 s, 20 successes and an empty queue. A signal while probing restores the proven rate and doubles the quiet period.
  - A success is one 2xx, quota-free response (HTTP), or a response with a usable result (JSON-RPC, including batches). 5xx and transport errors never count.
  - Quota is classified by `QuotaSignal` (message phrases or provider metadata; `-32005` alone is not enough, since Infura uses it for `eth_getLogs` result caps) and carried as `BlockchainClientError.quotaExceeded`. A terminal 429 still reports to the gate.
  - Retry delays are enforced by the next `adapt`, not `.retryWithDelay`, so a request cancelled during the delay doesn't hang. Per-request state is one lock-protected entry with a cancel tombstone; `requestResponse` resumes with `CancellationError` on cancel.
  - Sui gRPC: `rpc(.read | .submit)` gates each RPC (every pagination page), retries reads on `resource_exhausted`; submissions report but never replay. Electrum: gated `call`; broadcast never retried. Both use `ProviderKind` `.suiGRPC` / `.electrum`.
* **Consequences:** Backfill yields to balances, staking and approvals on a shared origin and still progresses. Worst case with every lane saturated at the 1/s floor is an average of one approvals admission per ~9 s (4/37 of the budget), not a per-request bound.
  - Quota phrases were checked against provider docs: Infura `-32005` ("daily request count exceeded", "project ID request rate exceeded"), Alchemy code `429` ("exceeded its compute units per second capacity"), QuickNode `-32007`/`-32008`/`-32011` ("request limit reached"). ElectrumX answers `-101 "excessive resource usage"` and then closes the session (seen in an Electrum bug report; not read from ElectrumX source). Fulcrum sends no error: it drops the connection, so it surfaces as a transport failure and is not classified.
  - Sui and Electrum retry loops share `QuotaRetry`; they are unit-tested through injected registries and a send override. A subscription that fails after its first message is not covered (it needs a real stream).
  - Live measurement (mainnet, watch-only, Etherscan key present, 2026-11-10; `Tests/LiveBackfillLatencyTests.swift`, opt-in via `/private/tmp/reefr-live-latency`). One account backfilling, lanes vs all lanes collapsed into one FIFO. **Pre-fix figures:** they were timed with a 200 ms polling loop that added up to one interval to each result, before completion was stamped inside the task, and have not been rerun.
    - Balances refresh: 1.03 s vs 1.03 s (vitalik.eth, 200 txs stored) and 0.42 s vs 0.43 s (test-junk #1). A 10 ms gap is below that timing error, so the two are indistinguishable. An earlier run showed a larger gain that did not reproduce.
    - Approvals: 18.7 s vs 20.9 s and 3.5 s vs 4.6 s (about 10-23% faster). Preliminary: a single run per case, same timing caveat.
    - One backfilling account issues one request at a time and most of the refresh goes to unpaced JSON-RPC, so little contention is expected. Contention grows with several accounts backfilling on one origin, which was not measured. vitalik.eth's full approvals scan did not finish in 45 s without a backfill, so its baseline is missing.
    - Only the lane run was repeated with the corrected timing (vitalik.eth balances 0.93 s, approvals 19.1 s; test-junk #1 0.34 s, 3.4 s). The FIFO side was not.
  - `ReefrWalletUITests-iOS` now builds with the macOS-only UI tests excluded (`iosUITestExclusions` in `Project.swift`); 6 of its 7 remaining tests fail because they assume the macOS UI.
