# ADR-072: NFTs tab and NFT sends

* **Date:** 2026-11-21
* **Status:** Accepted
* **Context & Problem:** Users can't see or send NFTs. NFT ownership has no common index across chains. EVM indexers lag behind the chain, and a send's outcome is unknown at broadcast, so a naive refresh could show a sent NFT again or hide one that never left.
* **Options Considered:**
  - EVM holdings from Blockscout `/addresses/{a}/nft`: one call, but the response carries no position, so a pending send can't be matched against it.
  - Alchemy NFT API: broad coverage, but it's a new service that needs a user key.
  - EVM transfer ledgers from Blockscout and Etherscan (chosen): holdings are recomputed from stored transfers, and the ledger itself proves whether a send was indexed.
  - Chain logic in the app on top of WalletKit's public APIs: needs no release, but splits chain code across two repos. Rejected; WalletKit 0.8.0 gets it.
* **Decision:**
  - **Scope.** EVM (ERC-721/1155), Solana (Metaplex), Sui, Aptos (Token V2, plus V1 listed only) and Cardano (CIP-25, CIP-68).
    - Not covered: Bitcoin Ordinals, Tron TRC-721, Solana compressed NFTs and Sui Kiosk-held objects.
    - Listed but not sendable: programmable NFTs, Aptos V1, Aptos V2 tokens that are soulbound or `non_transferrable_by_owner`, and Sui objects without `has_public_transfer`.
  - **WalletKit 0.8.0.**
    - `NFTListing.ownedNFTs` returns pages with an `NFTSnapshotPosition` taken from the same response. `NFTTransactionBuilding.buildNFTTransfer` builds the send.
    - EVM: `safeTransferFrom`, using the new dynamic `.bytes` case of `EthereumABIValue`.
    - Solana: `transferChecked` with amount 1. The envelope now carries `lastValidBlockHeight`.
    - Sui: `TransferObjects`.
    - Aptos: `0x1::object::transfer<0x4::token::Token>`, through the new `buildEntryFunction`.
    - Cardano: the existing native-asset transfer.
    - New request lane: `.nfts`.
  - **Inclusion rules.**
    - Solana: decimals 0, amount 1, and non-fungible metadata.
    - Sui: a Display with `name` or `image_url` on a type outside `0x1`/`0x2`/`0x3`. Display is presentation metadata, not a type check, so the Sui tab is captioned "Objects with display metadata" and each card shows the object type.
    - Aptos: V2 rows filtered by standard with no amount filter (their amount is 0); V1 rows need amount > 0.
    - Cardano: total supply 1 with CIP-25 metadata, or label 222. CIP-68 metadata comes from Blockfrost or else from the label-100 reference datum, decoded in Swift (no FFI change). If both fail, the asset is listed without an image.
  - **Store.** Four entities, added by lightweight migration and cascade-deleted with their account:
    - `NFTModel`, keyed by account, standard, collection and token id.
    - `NFTScanModel`: one per account and source, holding that source's cursor and whether it supplies the current snapshot.
    - `NFTTransferEventModel`: the EVM ledger, keyed by account, source, tx, `logIndex` and batch position.
    - `NFTPendingSendModel`.
  - **Snapshots.** Ownership is written only by a complete scan, and a failure writes nothing.
    - Ledger scans start 32 blocks below that source's cursor (block 0 the first time). The events from that window up are replaced and the holdings recomputed, all in one save.
    - Etherscan omits `logIndex`: a transaction with several events is resolved from its receipt, and a missing receipt fails the scan.
    - Blockscout is preferred, falling back to Etherscan. An account with an RPC override reads its own node's `eth_getLogs` first (`NodeLogNFTSource`): public indexers may not see its chain (a fork, a devnet).
    - A source becomes the snapshot source only after its own complete ledger exists.
    - Metadata (`tokenURI`/`uri`, `ipfs://`, `data:`) is best effort and retried daily. A metadata failure never removes a holding.
  - **Sends.**
    - A pending send is stored at broadcast. Send stays disabled until the sheet's confirmation wait or a later refresh settles it.
    - Success decrements the holding; a self-send records nothing. Failure deletes the pending send.
    - A confirmed send stays subtracted until the snapshot reflects it:
      - Ledger (Blockscout, Etherscan, node logs): it contains the send's event.
      - Aptos: the processor version is at or past the send.
      - Sui: the object is gone, or its version has moved past the one sent.
      - Solana: the read was served at or after the send's slot (`minContextSlot`).
      - Cardano: the send's inputs are no longer listed.
    - An unconfirmed send is dropped only on positive evidence that it can't land:
      - EVM: a synced transaction reused its nonce.
      - Cardano: an input was consumed by another transaction.
      - Sui: the object's pre-send version was consumed by another digest.
      - Or a listing ordered after expiry still shows the asset: Solana via the `getEpochInfo` slot, Aptos via the processor timestamp, Cardano via the tip read before the UTxOs.
    - Otherwise only "Forget Unconfirmed Send…" clears it.
  - **Signing.** Send requires a key store that can sign on the chain, and Trezor can't on Aptos or Sui (ADR-029).
  - **UI.**
    - An NFTs tab on all EVM chains plus Solana, Sui, Aptos and Cardano; an EVM chain without a source shows a notice.
    - A plain text table for now (Name, Collection, Token ID, Quantity, Status on Mac; text rows on iPhone). Image URLs are stored for a later designed UI, and there are no Penpot components yet.
    - Send uses the shared Transaction Sheet with an NFT row, a Quantity row (ERC-1155 or more than one held) and a Cardano Recipient ADA row.
* **Consequences:**
  - Blockscout's first scan pages an account's whole NFT history, and Etherscan needs a key.
  - Reorgs deeper than 32 blocks aren't handled.
  - A send whose indexer never catches up stays subtracted with "Waiting for …", which can't silently restore a sent NFT.
  - An EVM send replaced outside synced history stays locked until Forget.
  - ERC-721 `setApprovalForAll` is still not listed (ADR-048).
