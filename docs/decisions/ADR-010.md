# ADR-010: Bitcoin support

* **Date:** 2026-09-21
* **Status:** Accepted
* **Context & Problem:** Bitcoin breaks three assumptions the EVM/Sui implementations share: (1) one address per account — `BlockchainClientProtocol` is parameterised on a single `Address`, but a standard Bitcoin account is an xpub with external/change address chains discovered by gap limit; (2) account-indexed nodes — Bitcoin Core has no address index, so balances/history/UTXOs need a separate indexing server; (3) UTXO transactions — no nonce/gas model, so sending needs coin selection, a change output, and per-input sighashes/witnesses instead of one signed blob.
* **Options Considered:**
  - Backend: Electrum only (simpler, but push-based `headers.subscribe` and full-history-in-one-call, no HTTP fallback) vs. Esplora only (plain HTTPS, but paginated and no server push) vs. both, selectable per account (chosen — the two backends satisfy the same `BitcoinBackend` protocol seam, so `BitcoinClient` is written once against either).
  - Address identity: a new `Account.address`-adjacent field for the xpub vs. encoding the whole account (script type + xpub + BIP-32 origin) as an output descriptor string and reusing `Account.address` unchanged (chosen — no schema change, and `AnyBlockchainClient`'s generic `Address(string:)` bridging keeps working).
  - PSBT assembly/signing: hand-rolled in Swift (matching `EthereumTransactionBuilder`/`SuiTransactionBuilder`) vs. built on `rust-bitcoin`'s own `Psbt`/`Transaction`/`SighashCache` types in `walletkit-ffi` (chosen — `rust-bitcoin` was already a transitive dependency via `walletkit-trezor`, and hand-rolling BIP-143/BIP-341 witness assembly in Swift is an unforced correctness risk).
  - Address derivation cache: a persisted `BitcoinAddressModel` table (per the original plan) vs. an in-memory, per-`BitcoinClient`, gap-limit-20 `BitcoinAddressResolver` that re-scans via the backend each session (chosen for now — simpler, and the resolver already has to talk to the backend for balances/UTXOs regardless; revisit if repeated gap-limit rescans prove too slow against a slow public server).
* **Decision:**
  - `BitcoinDescriptor` (`wpkh(...)`/`tr(...)` for a local xpub-rooted account, `addr(...)` for watch-only/destination) is the account's `Address` type and its stable on-disk identity — no `Account` schema change.
  - Both native SegWit (BIP-84) and Taproot (BIP-86) are supported for our own receive/change addresses; sending *to* legacy/P2SH-wrapped addresses works, deriving our own as one does not.
  - `BitcoinBackendKind` (`.electrum`/`.esplora`) is a per-account setting (`Account.bitcoinBackend`), mirroring how `rpcURLOverride` already lets one account point at a non-default endpoint — set once at account creation, no edit-account flow, matching `rpcURLOverride`'s own asymmetry.
  - `ElectrumBackend`/`EsploraBackend` conform to one internal `BitcoinBackend` protocol; `BitcoinClient` (gap-limit resolution, history unioning, fee normalization) is written once against it. `isSupported(.transactionSubscription)` is the one place behavior forks (`backend is ElectrumBackend`); Esplora has no push transport.
  - PSBT assembly (`bitcoin_build_unsigned_psbt`), coin selection (`BitcoinCoinSelector`, Swift-side so selection policy is testable without an FFI rebuild), and signing (`BitcoinSignerFfi` — BIP-143 for `wpkh`, BIP-341 key-spend with the BIP-86 tweak for `tr`) all sit in `walletkit-ffi`/`WalletKit`, not the app layer.
  - Trezor signing hands the whole unsigned PSBT to the device's own `SignTx`/`TxRequest`/`TxAck` flow, which reads each input's owning key off the PSBT's `bip32_derivation`/`tap_key_origins`. This requires every input to carry `non_witness_utxo` (the full funding transaction), not just `witness_utxo` — confirmed against a real device, which independently verifies the spent amount and rejects a PSBT without it even for SegWit/Taproot inputs where `witness_utxo` alone would otherwise be BIP-174-sufficient.
  - `BitcoinTrezorSigner` reads the device's account xpub via a new `bitcoin_xpub` hardware call, always requesting mainnet-style (`xpub`) serialization regardless of the account's actual network — `walletkit-ffi`'s own `ExtendedKeyFfi` parser only recognizes `xpub`/`xprv` version bytes (it never network-tags its own serialized keys), so a real `tpub` string from the device fails to parse. Real network (mainnet/testnet/signet/regtest) is still tracked correctly by `BitcoinDescriptor`/`BitcoinNetwork` — this only affects the xpub's own text encoding, not address derivation or signing.
  - No new `TransactionHistorySource` (ADR-005) — both backends are already address-indexed, so `BitcoinClient` alone satisfies history without a separate backfill provider.
  - Test infrastructure: `make bitcoin-testing` provisions `bitcoind` (downloaded) and `electrs` — specifically Blockstream's `new-index` fork, the one with an Esplora-compatible `--http-addr`, since upstream `romanz/electrs` is Electrum-only and has no prebuilt binary for the fork either — once, ahead of the Swift build, the same way `make walletkit-ffi` provisions the XCFramework. `BitcoinNode` (in `WalletKitTesting`) only resolves the already-built binaries at test-run time.
* **Consequences:** Bitcoin mainnet/testnet/signet/regtest accounts work end to end (receive, balance, history, send, hardware signing) through either backend, verified against real `bitcoind`/`electrs`, not just a mock. Real infrastructure testing caught several bugs a mock backend structurally couldn't: Blockstream's `electrs` doesn't implement Electrum's verbose transaction decoding (fixed by decoding raw transactions ourselves via a new `bitcoin_decode_transaction` FFI call); both backends' `broadcast` used Ethereum's `0x`-prefixed hex instead of Bitcoin's plain hex (bitcoind's raw-tx decoder misparses the former); and the gap-limit address resolver double-counted a `.singleAddress` descriptor's balance (chain 0 and chain 1 resolve to the same address for it) and never rechecked previously-unused addresses for new activity (so a change address funded mid-session stayed invisible to a later balance query). Known limitations: no coin control/RBF/CPFP/multisig/PSBT import-export; no BTC/USD pricing (`getTokenPrice` throws, matching Sui); the per-account backend choice has no edit-account UI; a watch-only xpub import (rather than one address) is a follow-up, since it would also need the UI to ask which script type the xpub is for.
